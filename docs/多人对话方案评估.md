# 多人对话方案评估（2026-11-08）

> 目标：在现有单人聊天之外，开一个「多人聊天」界面。可指定谁先说、每个角色绑自己的世界书、
> 支持自动对话，用户也能扮演其中任意一个角色。
>
> 本文只做可行性拆解与分期，不含实现。结论在最后一节。

---

## 1. 现状：单人语义已经渗进了三层

任何一处不改，多人都会"能跑但不对"。

| 层 | 现在的假设 | 位置 |
| --- | --- | --- |
| 数据 | 一个会话 = 一个角色｜消息只有 `user` / `ai` 两侧 | `SessionDoc`、`SessionAction` |
| 生成 | `{{char}}` 永远指当前角色；世界书/预设/正则按**会话**绑定 | `assemblePrompt`、`SessionBindingStore` |
| 界面 | 气泡按 `role == "user"` 左右二分 | `ChatAdapter`、`ChatItem` |

另外两个隐藏假设：

- **`currentCharacterId` 是全局单例**。切会话时 `setActive(characterId)` 会把全局当前角色改掉
  （`assets` store、角色卡库、生成入口都读它）。多人必须换成"会话内成员集合"，
  这是破坏性改动，不能靠加字段绕过。
- **变量是会话级**。所有角色共用一张变量表 —— 多人下"好感度"会互相污染。

---

## 2. 物理隔离能做到什么程度（关键）

用户的要求是"只有那个角色知道的事，物理隔离不让其他角色知道"。要拆成三层看：

| 层次 | 能否隔离 | 做法 | 代价 |
| --- | --- | --- | --- |
| **注入隔离** | ✅ 能，且干净 | 生成 A 的回合时，只把 `A 的私有世界书 + 公共世界书` 放进 system | 低（改组装函数） |
| **上下文隔离** | ⚠️ 只能做浅层 | 历史里 B 说过的台词仍然在上下文里；要真隔离得给每个角色维护"已知信息摘要"，并把不属于 A 的历史做遮蔽/改写 | 高，且容易让模型表述错乱 |
| **变量隔离** | ✅ 能 | 变量表加命名空间 `char:<id>:<key>`，公共变量放 `global:` | 中（所有读写点都要带命名空间） |

**建议：先做「注入隔离 + 变量隔离」，上下文隔离明确不做。**

理由：世界书本身就是"设定注入"，绝大多数"只有他知道"的需求（身世、暗线、隐藏身份）
写在世界书条目里就够；真要防"B 的台词泄露"，靠一句系统提示
（"你不知道其他角色未公开的信息，不要替他们说出秘密"）比事后遮蔽历史更稳。
真做上下文遮蔽，模型会因为"缺了几段对话"而逻辑断裂，反而更出戏。

## 3. 数据模型

### 3.1 会话加成员表（新字段，raw 兜底保证老数据可读）

```
SessionDoc
  members: List<Member>        // 新增，空 = 单人（老会话天然兼容）
  speakerOrder: List<String>   // 发言顺序，存 memberId
Member
  id: String          // 会话内唯一，不用角色卡 uid（同一张卡可以演两个角色）
  characterId: String // 指向 assets.characters 的 _uid
  name: String        // 覆盖卡上的名字（"旁白""酒保"这种临时角色）
  presetId: String?   // 该角色用哪套预设；null = 会话默认
  connectionId: String? // 该角色用哪个 API（多角色分别选 API 的落点）
  worldBookIds: List<String>  // 该角色的私有书
  regexGroupIds: List<String> // 该角色的显示正则
```

### 3.2 消息加发言人

```
SessionAction
  speakerId: String   // 新增；空 = 旧数据，按老逻辑（user/ai 二分）
```

`SessionAction.toJson()` 已经是"raw 打底再覆盖已知字段"，加字段零迁移成本。
**前提是分支/复制不能清 raw** —— 见 §14.1 修掉的那个 bug。

### 3.3 绑定从"会话级"改成"成员级"

`SessionBindingStore` 现在是 `sessionId -> Binding`。改成：

```
sessionId -> {
  default: Binding,              // 公共：所有人都吃的世界书/正则
  members: { memberId: Binding } // 各自的私有书
}
```

公共书用于"世界观设定"，私有书用于"只有他知道"。生成时取**并集**：
`default.worldBookIds + member.worldBookIds`。

---

## 4. 生成层：一次生成 = 一次"谁在说话"的决策

### 4.1 组装

现在 `assemblePrompt(char, user, history, books, preset)`。多人版本：

```
assembleMultiPrompt(
  speaker: Member,        // 决定 {{char}}、角色卡、私有书、预设、API
  audience: List<Member>, // 决定"其他人"是谁（可写进提示词：在场角色列表）
  history,                // 全部历史，但每条带 speakerId
)
```

关键改动：

1. `{{char}}` 绑定到 `speaker.name`，`{{user}}` 绑到"当前用户扮演的角色"（可能不是本人）；
2. 历史里每条消息前加发言人标签（`【A】…`），否则模型分不清谁说的；
3. 私有世界书只注入 speaker 的；
4. 预设仍是整套（一套预设服务一次生成），但**预设里的 `{{char}}` 语义变了** ——
   同一套预设会被不同角色复用，写死了"你是 {{char}}"的预设照样能用，写死了具体性格的会打架。
   这点要在 UI 上提示，不是代码能解决的。

### 4.2 谁说话（编排）

| 模式 | 实现 | 难度 |
| --- | --- | --- |
| 手动（用户点谁） | 点成员头像 → 以该成员身份生成 | 低 |
| 顺序轮询 | 按 `speakerOrder` 依次，跳过刚说过的 | 低 |
| 随机权重 | 每个成员一个权重 | 低 |
| LLM 选人 | 多一次小请求："下一个该谁说话，只回名字" | 中（多一次延迟与费用） |
| 用户插话 | 用户随时以自己扮演的角色发言，打断轮询 | 低 |

**建议 MVP：顺序轮询 + 手动指定 + 用户插话**，LLM 选人放到后面。

### 4.3 自动对话

本质是"连续触发 N 次生成"，要注意：

- 每次生成结束才能决定下一个（不能并发，否则上下文乱）；
- 要能随时停（现有 `controller.stop()` 只停当前请求，需要一个"自动对话进行中"的标志）；
- 每 N 轮要防止上下文爆炸，正好复用自动摘要，但**摘要必须保留发言人**。

---

## 5. 摘要：现在会把两个人的台词糊成一个人

`SummaryBlock` 只有 `role + text`。多人摘要如果不带发言人，会得到
"两人商量后决定去码头"这种无法还原的句子，后续生成会错乱。

改法：`SummaryBlock` 加 `speaker`，摘要提示词要求"按 `【名字】` 标注谁说了什么"。
这是小改动，但**必须在多人上线前做**，否则摘要一开就污染长期记忆。

---

## 6. 界面

复用现有聊天页，但要解决"一人一列"的问题：

| 元素 | 现在 | 多人 |
| --- | --- | --- |
| 气泡 | `role` 二分左右 | 按 `speakerId` 取色/取头像，仍左右分（用户扮演的角色在右） |
| 名字 | 无 | 气泡上方小字（同一个人连续说话可省略） |
| 成员条 | 无 | 顶部横向头像条：点头像 = 以他身份说话，长按 = 改配置 |
| 顺序 | 无 | 成员条支持拖拽排序，或单独一个"发言顺序"小窗 |
| 设置 | 会话 ⋯ 菜单 | 新增"成员管理"页：加/删角色、绑书、绑预设、绑 API |

`ChatItem` 只需加 `speakerId` / `speakerName` / `speakerColor` 三个字段，
`ChatAdapter` 的左右判断从 `role == "user"` 改成 `speakerId == selfMemberId`。

## 7. 分期与工作量

| 期 | 内容 | 估时 | 风险 |
| --- | --- | --- | --- |
| P0 | 数据层：members / speakerId / 成员级 binding（含迁移与 raw 兼容） | 3–4 天 | 低 |
| P1 | 生成层：按 speaker 取卡/书/预设/API，历史加发言人标签 | 4–5 天 | **高**（`{{char}}` 语义、currentCharacterId 单例） |
| P2 | 界面：成员条、气泡发言人、成员管理页 | 4–6 天 | 中 |
| P3 | 自动对话 + 摘要带发言人 + 变量命名空间 | 4–6 天 | 中 |
| P4 | LLM 选人、上下文遮蔽（可选） | 5–8 天 | 高，建议先不做 |

**MVP（P0–P2）≈ 2 周；含自动对话与摘要适配 ≈ 3 周。**

对比「每角色单独 API」：那只是 P0 里的一个字段 + `GenBridge` 传参，
因为 `req.config` 的优先链路已经通了，**单独做的话 1 人日**。

---

## 8. 建议的落地顺序

1. **先做「每角色单独 API」**（1 天）。它是独立价值，且能把 `ConnectionStore` 的
   "按 uid 取配置" 这条路径先跑通 —— 多人要用同一套。
2. **再做 P0 + P1 的最小闭环**：两个角色、手动指定谁说话、各自绑书、
   生成结果写进同一个会话。这时候界面可以先丑（用现有气泡，只在开头加名字）。
3. **验证"物理隔离"是否真的有效**：给 A 一本私有书（写一个只有 A 知道的口令），
   问 B 这个口令是什么，B 必须答不出来。这是唯一能证伪的测试。
4. **最后做 UI 与自动对话**。

---

## 9. 结论

- **技术上没有死结**，最硬的骨头是 `currentCharacterId` 全局单例和 `{{char}}` 的语义，
  两者都在生成层，不在数据层。数据层因为 `raw` 兜底，加字段几乎零成本。
- **"物理隔离"要限定在"世界书注入"这一层**。上下文层做真隔离会伤可读性，不建议。
- **工作量**：MVP 2 周、完整 3 周（按单人开发、每天有效 4–5 小时估）。
- **前置条件**：分支必须保留 `raw`（已修）、摘要必须带发言人（未做，多人上线前必做）。
