# 原生优先架构方案（Native-First）

> 目标：把 WebView 从「整个 App」缩成「SillyTavern 兼容内核 + 生成引擎」，
> 其余全部原生。桥从「每个功能一套」收敛成 **2 条固定通道**。

---

## 1. 为什么要改

现在的形态是「原生外壳 + WebView 里跑整页」，每个功能都要单独设计一份桥：

```
会话列表 ──┐
角色导入 ──┤
生图回调 ──┼── 各自一套 JSON 协议 ──► 协议越多，字段漏传/解析错的机会越多
配置读写 ──┤
消息操作 ──┘
```

每加一个功能就多一份协议、多一处字段映射，出错面随功能数线性增长。

改成原生优先后，桥只剩两条，且都是**单向、无状态、一次性**的：

```
        ┌──────────────────────────────┐
        │  原生层（权威数据 + 全部 UI）  │
        │  JSON 文件存储 / RecyclerView │
        └───────────┬──────────────────┘
                    │  ① 生成通道（请求 → 流式回包）
                    │  ② 迁移通道（老 IndexedDB → 原生，一次性）
                    ▼
        ┌──────────────────────────────┐
        │  Web 层（只做 ST 兼容 + 生成）│
        │  预设 / 正则 / 角色卡 / 世界书 │
        │  / 变量 / 宏 / 请求组装       │
        └──────────────────────────────┘
```

**关键：桥不做状态同步。** 原生把自己的状态打包成一次请求发过去，
web 处理完把结果吐回来，双方不持有对方的镜像数据 —— 这从根上消除了
「两边各存一份、改一处忘一处」这类问题的来源。

---

## 2. 边界划分（哪些必须留 web）

| 能力 | 归属 | 理由 |
| --- | --- | --- |
| 预设（prompt preset） | **web** | SillyTavern 的 prompt 组装语义（顺序、注入位、相对位置）极其繁琐，重写风险最高 |
| 正则脚本（regex scripts） | **web**（执行）/ stcore（显示侧已复刻） | 同一份脚本要同时作用于「送模型的文本」和「显示文本」，必须同一实现 |
| 角色卡格式（V1/V2/V3、PNG 内嵌） | **web 解析**，原生已有只读解析器可复用 | 格式兼容层不能动；原生解析器只用于列表展示，不改格式 |
| 世界书（lorebook / 触发词） | **web** | 触发扫描 + 递归激活 + 位置注入，语义复杂 |
| 变量（global / chat） | **web 为权威**，原生只读快照 | 变量会被正则/世界书/预设同时读写，必须单点 |
| 宏替换 / 思维链剥离 / 图片标记 | stcore 已有实现 | 显示侧已经对齐，继续用 |
| **生成请求本身** | **web** | 依赖以上全部，且要复用现有重试/流式/错误处理 |
| 会话 / 消息 / 角色库 / 配置 / 标签 / 图片库 | **原生** | 纯数据 + 纯 UI，没有 ST 语义 |
| 聊天渲染 / 气泡 / 富文本 / 长按操作 | **原生** | 已实现（RecyclerView + Spannable） |
| 设置类页面（API、风格、外观） | **原生** | 纯表单，直接读写原生存储 |

一句话：**凡是「SillyTavern 会读会写」的东西留 web；凡是「App 自己的壳」全原生。**

## 3. 数据存储（原生权威）

### 3.1 为什么不用 SQLite

- 会话本身就是「一条时间线」，天然是一个文档，拆表反而要做 join；
- 单会话几千条消息，JSON 读取在手机上仍是毫秒级；
- 与 web 端数据形状 1:1，迁移只是「搬文件」，不做字段翻译；
- 出问题时用户能直接把文件拿出来看/改/备份，比数据库友好。

### 3.2 目录结构

```
filesDir/
  data/
    sessions/
      index.json                  # 列表页用：id/title/count/updatedAt
      <sessionId>.json            # 单个会话完整内容
    characters/
      <uid>.json                  # 角色卡（含头像文件引用）
      <uid>.png                   # 头像原图（可选）
    config/
      llm.json                    # 对话模型配置（多套 + 当前选中）
      image_api.json              # 生图接口
      image_style.json            # 出图风格
      appearance.json             # 外观（已存在）
    assets/
      <hash>.jpg                  # 图片资产（配图/生图产物）
```

### 3.3 兼容策略：**未知字段原样保留**

这是整个迁移里最关键的一条。

原生解析 web 数据时，只强类型化「自己认识的字段」，其余全部塞进 `raw`，
写回时先铺 `raw` 再覆盖已知字段。效果：

- 原生暂时不支持的字段（比如 `summaries[].targetWords`、图片的 `storage`）
  **不会因为过一次原生就被抹掉**；
- 将来 web 侧加了新字段，老版本 App 打开也不会丢数据；
- 迁移可回退：把文件原样交回 web 也能读。

### 3.4 写入方式

- 先写 `<file>.tmp` → `fsync` → `rename`，避免写到一半断电留半个 JSON；
- `index.json` 只在标题/条数/时间变化时更新，不随流式增量重写；
- 流式生成期间草稿单独走 `draft` 字段，每 1.5s 落一次（不是每个 token 都写）。

## 4. 生成通道协议（第二阶段）

原生只发**一次**请求，web 用回调吐**多条**增量：

```
原生 → web : __dhpEngine.run(requestJson, token)
web → 原生 : AndroidNative.onEngineEvent(token, eventJson)   // 多次
```

```jsonc
// 请求
{
  "token": "e-1730000000-1",
  "sessionId": "s_xxx",
  "userInput": "我推开门",
  "history": [ { "role": "user", "content": "…" }, … ],   // 原生权威历史
  "charId": "c_xxx",
  "config": { "presetId": "...", "lorebookIds": ["..."], "variables": {...} },
  "stream": true
}

// 事件
{ "type": "delta", "text": "…" }
{ "type": "reasoning", "text": "…" }
{ "type": "done",  "text": "完整正文", "usage": {...} }
{ "type": "error", "message": "…", "retryable": true }
```

约定：
- `token` 由原生生成，web 原样回传 —— 原生据此丢弃过期请求的迟到事件；
- `done` 一定发（成功或失败都要终结），否则原生会一直显示「生成中」；
- 图片仍走已有的 `onImageResult` 回调（同一条通道的不同 event type）。

### 4.1 实际落地的接口（以这版为准）

上面的 `__dhpEngine.run` 是初版设想，实现时按"少一层 JSON 分派、少一次解析"
改成了 4 个独立回调，语义等价但原生侧更好写：

```
原生 → web : __dhpGen.generate({ requestId, sessionId, messages, userInput,
                                 imageInstruction, imageInstructionMax })
web → 原生 : AndroidNative.onGenDelta(requestId, 全文)      // 约 80ms 一次
             AndroidNative.onGenDone(requestId, 全文)
             AndroidNative.onGenError(requestId, message)
             AndroidNative.onGenStopped(requestId)
原生 → web : __dhpGen.stop(requestId)
```

三条必须遵守的约定（都踩过）：

1. **delta 推的是全文不是增量**。原生直接整段替换，丢一个包也不会错位；
2. **节流在 web 侧做**（80ms）。每个 token 都过一次 JS→Java 桥，长回复能让主线程卡住；
3. **`stop` 一定要有终结回调**。即使 web 还没真正发出请求（正卡在变量写宏），
   也要立刻回 `onGenStopped`，否则原生永远停在"生成中"。

另外三个一次性读取接口（不进生成链路）：

```
__dhpGen.displayConfig(sessionId) → 正则/变量/宏上下文（渲染用）
__dhpGen.imageConfig()           → 生图 + 标签优化配置快照（自动配图用）
__dhpGen.assetCatalog()          → 预设/世界书/角色清单 + 当前启用项
__dhpGen.setActive(json)         → 切"启用哪个"（数据仍在 web）
```

## 5. 迁移计划（每阶段都可独立运行、可回退）

### 阶段 1：数据层原生化（本次）
- stcore：`SessionDoc` 等数据模型（强类型 + raw 兜底），配 JVM 单测；
- app：`SessionStore` 文件存储（原子写、索引、按需加载）；
- web：`exportDump()` 一次性导出全部数据；
- app：`MigrationImporter` 把 dump 落成原生文件，**只读不改 web 数据**。

此时 UI 仍走现有桥，但数据已经有原生副本 —— 出问题直接删目录回退，零风险。

### 阶段 2：读写路径切换
- 会话列表 / 聊天页改读原生存储；写操作（发送、编辑、删除）也落原生；
- web 只在生成时接收「历史 + 配置」的一次性快照；
- 双写期：原生写完后异步通知 web 更新（单向，web 不反向写）。

### 阶段 3：桥收敛
- 删除 `getSessions` / `openSession` / `getSnapshot` / `getConfigBundle` 等业务桥；
- 只留 `__dhpEngine.run` + `__dhpData.exportLegacy`（迁移用完即可删）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 迁移丢字段 | 用户数据损坏 | `raw` 兜底 + 导入前后条数/字节校验 + 原数据只读不删 |
| 生成通道流式中断 | 消息半截 | 原生侧保留 draft，`done` 未到就显示「中断，可重试」 |
| 两套渲染不一致 | 看到的和模型输出的不一样 | 显示侧继续用 stcore（已与 web 对齐，22 项单测） |
| 老版本降级 | 新数据老 App 读不了 | 文件格式带 `schemaVersion`，老版本只读不写 |
| 配置迁移后 web 读不到 | 生成用错 key | 阶段 2 前 web 仍是配置权威，原生只读镜像 |

## 9. 单一数据源：版本、图片、自动配图

这一节回答三个容易做错的地方。三者的答案都来自同一条原则：
**会话只有一份，存在原生；web 每次只拿到"当下这一刻要发出去的那份"。**

### 9.1 版本切换为什么不会不同步

数据形状（`stcore.session.SessionAction`）：

```
action.user / action.ai          ← 用户当前看到的这一版
action.variants[]                ← 历史版本，[0] = 最新
action.variantIndex              ← 当前指向 variants 的第几个
```

- 点「‹ ›」只改 `user/ai/variantIndex`（`SessionEditor.switchVariant`）；
- **导出给 web 时只读 `user/ai`，`variants` 一个字节都不外发**
  （`SessionHistory.export`）。

于是"切了版本，模型还按旧版本答"这类问题从根上不存在 —— 生成时看到的就是
用户眼前这篇文字。也不需要"切版本时通知 web"这种同步消息。

### 9.2 图片为什么不进上下文

- 正文里只有占位符 `[[IMG: 画面描述]]`；
- 图片本体挂在 `action.images[]`（`assetId` / `nativeLocalPath`），
  与正文是两个字段，**从来不在 content 里**；
- 导出历史时 `SessionHistory` 内部调 `stripImageMarkers()`，
  把占位符连同内联 base64 的 markdown 一起剥掉。

效果有三：
1. 模型看不到自己上次插了什么图，不会自我强化"每段都配图"；
2. 不占 token；
3. 重新生成时不会因为图片文本变化而产生"看起来一样、实际不同的上下文"。

### 9.3 自动配图为什么不走 web 生成通道

自动配图 = **把一段正文交给对话模型打标签** + **拿标签调一次生图接口**。
这两步跟 ST 预设、世界书、正则、变量全都无关：请求体固定、返回结构固定。

所以原生直接做（`imagegen/AutoImageService`）：

```
正文 ──plan()──► 每个 [[IMG: 描述]]
                    ├─ skipOptimization ? 用描述 : 调 chat/completions 转标签
                    ├─ finalPrompt()：画师串 → 质量词 → 主体标签（去重）
                    └─ 逐个候选端点试 → 成功即落盘 → 回调一张
```

配置只在打开会话时通过 `__dhpGen.imageConfig()` 读一次快照，之后不再问 web。
好处：不占 web 的生成队列、不依赖页面在不在前台、失败重试自己控制。

### 9.4 「启用哪个」放在哪

| 项 | 内容存哪 | 谁决定启用 |
| --- | --- | --- |
| 预设 | web（ST 兼容 JSON） | `currentPresetId`，web 存，原生可改 |
| 世界书 | web | `currentWorldBookIds[]` |
| 正则分组 | web | `currentRegexGroupIds[]` |
| 角色卡 | web（格式兼容层）+ 原生缓存用于列表展示 | `currentCharacterId` |
| 会话 / 消息 / 版本 / 配图引用 | **原生** | 原生 |

原生「引擎设置」页只做勾选（`EngineSettingsActivity` → `__dhpGen.assetCatalog/setActive`），
不复制内容。这样两边永远不会分叉：用户改完网页资产，原生读到的就是同一份。
