# 原生化边界（哪些必须过桥，哪些已经原生）

> 原则（2026-11-07 与用户确认）：
> **能不用桥就不用桥**。桥只保留"为了兼容 SillyTavern 格式"的服务端逻辑，
> 因为那套解析/拼装逻辑在 web 引擎里已经跑通、且必须与 ST 行为逐位一致。
> 其余一律原生实现。

## 二·五、引擎 WebView 必须挂在前台窗口（踩过的坑，务必别改回去）

**症状**：设置页里「新建运营商」「重命名」「保存参数」点了像没反应；但手动点一下
右上角「刷新」，数据其实已经写进去了。生图风格、资产条目也偶发同样现象。

**根因**：引擎是 MainActivity 里那个 1dp、`alpha=0` 的 WebView。它只属于创建它的
窗口。一旦进入设置/资产等**另一个 Activity**，MainActivity 窗口退到后台，Chromium
就把页面判成 `document.hidden=true` / `visibilityState=hidden`，冻结 JS 定时器与
部分异步任务。于是 `__dhpApi.command()` 发出去了、IndexedDB 也写成功了，但
`AndroidNative.onApiResult` 迟迟不回，原生列表不会自动刷新。

**诊断办法**（这次就是这么定位的）：

```bash
adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>
curl -s http://127.0.0.1:9222/json/list      # 拿 webSocketDebuggerUrl
# CDP Runtime.evaluate 里跑：
#   document.visibilityState                       -> "hidden"
#   window.__t=0; setTimeout(()=>window.__t=1,300) # 2 秒后仍是 0
#   Promise.resolve().then(()=>...)                -> 微任务照常执行
```

微任务能跑、定时器不跑，就可以确定是后台页节流，不是桥代码写错。

**解法**（两部分，都在原生侧）：

1. `DhpApp` 用 `ActivityLifecycleCallbacks` 在每个 Activity 的 `onStarted/onResumed`
   调 `MainActivity.attachEngineTo(activity)`：把**同一个 WebView 实例**重新 attach 到
   当前前台窗口的 decorView（一个带 tag 的 1dp 容器）。幂等，业务页面零改动。
   实测进设置页后 `visibilityState=visible`、定时器正常，命令回调立刻到达。
2. `EngineBridge.fetch` 内置有限重试（约 6 秒）：冷启动时 Vue 应用还没把
   `window.__dhpApi` 挂上，同步取值只会拿到 null。以前页面显示「引擎还没就绪」
   要用户自己点刷新，现在自动等到就绪再回调，所有取值页一起受益。

> 注意：WebView 尺寸给 1dp 而不是 `GONE` 仍有必要（GONE 在部分机型直接停 JS），
> 但**只做到 1dp 不够**，宿主窗口在前台才是关键。

## 二·六、配置已搬原生（2026-11-07，别再改回桥）

**结论**：运营商 / 模型 / 风格这些配置只是 `baseUrl / apiKey / model / 备注名`
几串字符串，跟 ST 兼容层（预设 / 世界书 / 正则 / 宏 / 变量）毫无关系。
以前让原生设置页绕 WebView 读写 Pinia store，纯粹是「网页版先有一套 store，
复用最省事」，不是技术必需；副作用就是二·五那个后台冻结坑。

现在的数据流：

```
配置页 ──读──> ConnectionStore（files/connection_store.json，原生权威源）
   │
   └──写──> ConnectionStore.apply(cmd) 本地执行 + 落盘
              ├─> NativeBridge.fireLocal(kind=原命令名) 触发页面原有 load()
              └─> applyNativeConfig(镜像) 单向通知引擎（不等回包）
生成请求 ──> GenBridge.request 带 req.config，并补推一次镜像
```

要点：

1. **文档形状与 web store 同构**（`llm.configs / providerNotes`、`image.apiConfigs
   / styleConfigs / autoImage`），故意不建 Kotlin data class —— 老数据里的
   `novelaiToken / novelaiModel / endpoint / providerId` 等历史字段直接透传，
   不会因为漏映射而丢。首次启动 `exportNativeConfig()` 整份搬一次，之后不再用。
2. **四个设置页零改动**：`EngineBridge.fetch` 对三个配置 fn 直接返回本地渲染的
   快照（`renderConfig / renderImageConfig / renderImageStyle` 复刻 web 的三个
   summary 函数）；写命令本地执行后用 `fireLocal` 发一条与原桥回包同形状的
   结果，页面照旧 `loadConfig()`。改渲染逻辑请同步检查
   `src/bridge/generateService.ts` 里对应的 summary 与 `apiCommand` case。
3. **引擎只读镜像**：`window.__dhpNativeConfig` / `__dhpRuntimeLlm`，
   `generate / buildMessages / imageConfig / optimizeImagePrompt` 改读它；
   刻意**不写回 Pinia store** —— 两份权威源迟早分叉，且 store 落盘是异步的。
   网页版独立运行（没有注入）时自动回退到 store，行为不变。
4. **ST 兼容层一个字没动**：`assemblePrompt`、世界书触发、正则、宏、变量
   仍走引擎，这是兼容 SillyTavern 的底线。
5. 拉模型列表也搬到了 `ModelListClient`（OkHttp），配置页不再需要 WebView 活着。

**验证手法**（可复现）：CDP 里执行 `window.__dhpApi = undefined` 把桥整个摘掉，
回原生页点「刷新」仍能列出全部运营商，新建/重命名也立即生效 —— 证明零依赖。
恢复后 `window.__dhpNativeConfig` 应能看到同步过来的全部配置。

下一步想彻底去掉这条单向通知，就做下面第三节的第 1 项（提示词组装 +
`/chat/completions` 一起搬原生），那时引擎连 apiKey 都不需要。

## 二·七、生图渲染器与场景隔离（2026-11-07）

**为什么加渲染器**：之前所有生图请求都发 OpenAI 的 `{model,prompt,size}`，
选了「砂糖」这类 NovelAI 中转时 `sampler / steps / scale / negative_prompt`
全部被丢掉，看起来像「参数选了没用」。实际各家参数语义完全不同：

| 引擎 | id | 请求体要点 |
|---|---|---|
| NovelAI 中转 / 官方 | `novelai-relay` / `novelai` | `{input,model,action,parameters}`，按模型代际裁剪字段；V4 有 `autoSmea`，V3 有 `sm/sm_dyn`，V2 不认 `noise_schedule` |
| 本地部署（SD/ComfyUI 包装） | `local` | 尺寸只认 `size: "832x1216"`，可选 `steps/cfg_scale/sampler/negative_prompt` |
| 通用 OpenAI 兼容 | `custom` | 字段越少越不容易被拒 |
| DALL·E | `dall-e` | 固定尺寸档位，不认采样器 |

实现在 `stcore/imagegen/ImageEngineSupport.kt`（纯逻辑、无 IO、可 JVM 单测），
字段裁剪逐条对齐 web 端 `src/engine/novelai.ts` 的 `buildNovelAIRequest`。
`ImageEngineSupport.candidateUrls` 复刻 web 的端点探测，中转站把
`/ai/generate-image` 挂在哪个前缀都不用用户猜，失败自动换下一个。

**三条出图路径全部接上**：标签生图（`NativeImageGenActivity`）、聊天 🎨 快捷生图
（`NativeChatActivity.generateQuickImage`）、自动配图（`AutoImageService`）。
最后一条的参数经 `__dhpGen.imageConfig()` 下发，因此 web 侧 `imageConfig()`
新增了 `engine / steps / cfgScale / sampler / noiseSchedule` 字段，
`stcore` 的 `NativeImageConfig` 同步解析。

**场景隔离**：对话生图与标签生图各记各的选中接口
（`image.sceneApiIds.chat` / `.tag`）。`imgUseApi` 带 `scope`：
`chat` 同时写 `currentApiId`（网页自动配图认它），`tag` 只写自己的槽位。
`imgSetEngine` 按 `baseUrl` 分组给同一运营商的所有模型设渲染器；
`imgSaveSize` 把小图档位同时写进当前接口与当前风格，风格页和标签页共用。

**界面约定**：出图页不再出现地址 / 密钥 / 裸模型输入框，只显示
「运营商 · 模型」，点一下直接列当前运营商下的模型（末尾可换运营商）。
图片大小只给小图快捷档位（`SIZE_PRESETS`，全是 8 的倍数）。

## 二·八、ST 兼容层子条目与配置管理（2026-11-07 晚）

**预设 / 正则仍在引擎**，但原生 UI 要能逐条开关、编辑、新建、删除。
`assetsDetail()` 现在把 `presets[].prompts`（含 enabled）与
`regexGroups[].scripts` 明细全带出来；命令 `preset*Prompt` / `regex*Script`
走桥到 `apiCommand`，语义留在兼容层，原生不复制第二份数据。
资产页三类资产统一成「组头展开 → 子条目卡片（快捷开关 + 点开编辑 + 长按删除）」。

**预设单条启停的坑**：ST 预设的 enabled 有两处 —— `prompts[].enabled` 与
`prompt_order[].order[].enabled`（parsecard 的 `listPromptEntries()` 读后者，
assembler 阶段 1 优先用它）。只改一处会「界面显示关了但提示词还在」。
`syncPromptEnabled()` 遍历 prompt_order 的所有历史形态（数组 / 对象 / 纯 id 数组）
同步两处；新建与删除子条目同样要同步 order，否则新条目不进提示词、
删掉的 identifier 还留在顺序表里。

**正则两层开关**：组用 `currentRegexGroupIds` + `group.enabled`（`setActive` 同步两者，
`flattenForEngine` 先按 `group.enabled` 过滤），组内脚本用 `scripts[].disabled`。

**配置管理批量操作**：`llmRemoveModels` / `llmRemoveProvider` /
`imgRemoveApis` / `imgRemoveProvider` 全在 ConnectionStore 本地执行（零桥）。
删完必须修 `currentConfigId` / `currentApiId` 与 `sceneApiIds.chat/.tag`，
否则会留下悬空 id，下一次出图/生成才炸。

**标签页**：APK 里的 `novelai-tags.json` 一直是全量 21097 条，之前是 UI 只取 12 条
还把 12 当总数显示。`TagLibrary.count()` 负责总量，`search(limit)` 只管分页。
已选标签以中文 chip 展示（可删可清空），请求体只拼英文 tag；生成按钮与结果图
放在标签列表**之前**，列表再长也不会把出图结果顶出屏幕。

**会话删除**：`SessionStore.delete()` 早就有了，补的是 UI —— 列表长按与聊天 ⋯ 菜单，
删前二次确认，聊天页删除时顺带清掉该会话的专属背景图。

**提示词模型两级选择**：`getImageConfig` 快照的 `llmConfigs` 增
`providerKey` / `providerName`；`ChatImageConfigActivity.pickLlm()` 先选运营商再选模型，
选中的标签也带运营商名，避免多家同模型名时分不清是哪一家。

## 三、下一步原生化的候选（按收益排序）

1. **提示词组装**移到 stcore：`assemblePrompt` 已有清晰的输入输出，配一组
   与 web 相同的测试向量（同输入 → 同 prompt 字符串）就能安全替换；
   替换后生成链路只剩"HTTP 流式请求"，可以彻底原生（stcore 已有 OkHttp）。
2. **资产存储**原生化：worldbook/preset/regex 的 JSON 直接用 Kotlin 读写，
   桥只保留"导入解析"这一件事（ST 格式兼容入口）。
3. **变量表**：stcore 已有变量引擎，把会话变量落盘原生化。

## 四、渲染策略说明（为什么用内嵌 WebView）

同类产品（如 Tavo）也是「原生外壳 + 消息 HTML 由 WebView 渲染」，因为它能：
- 真正吃下美化正则产出的 `<style>`/`<div>`/`flex`/渐变，而不是把 CSS 当正文；
- 保留 ST 社区美化卡的视觉一致性（web 端打磨过的效果直接复用）。

我们的实现细节：
- 只有"像 HTML"的消息（含 `<style>` 或 ≥2 个块级标签）才走 WebView，
  普通 Markdown/纯文本仍用 TextView（快、可选中复制）；
- 每气泡独立 WebView，禁文件访问/禁跨域跳转/禁 DOM 存储；
- **脚本默认剥离**（`<script>` 与 `on*` 属性），设置里可显式打开；
- 高度按 `scrollHeight × density` 二次测量，长消息不会被截断。
