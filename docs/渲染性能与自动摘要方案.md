# 渲染性能优化 + 自动摘要 设计方案

> 分支建议：`feat/render-pipeline`（从 `feat/ui-beautify` 切出，单开，防意外）
> 本轮定位：**只出方案，不动代码**。方案确认后按 P1→P3 分阶段落地，每阶段可独立验收、可独立回滚。
> 前置事实：用户可见界面 = 原生 Kotlin/Java；`src/`（Vue）只是 ST 兼容引擎，跑在隐藏 WebView 里，用户看不见。

## 0. 先校准一个认知（很重要，别改错层）

「电脑端是单线程，所以卡」这个判断**只对了一半**，真正的瓶颈排序和直觉不一样：

| 现象 | 真实原因 | 证据 |
| --- | --- | --- |
| 长会话滚动掉帧、打开卡 | 原生 `ChatController.render()` **每次全量重建整个会话**，且每个流式片段都触发一次 | `chat/ChatController.kt:181-264`、`:428-432` |
| 滚动时一顿一顿、内存飙高 | **每个 item 布局里都内嵌一个 WebView**（`msg_html` 即使 `GONE` 也已经实例化），同屏 10 个 ViewHolder = 10 个 WebView；滚出再滚回还要 `loadDataWithBaseURL` 重载一次 | `chat/ChatAdapter.kt:223-290`、`res/layout/item_chat_message.xml:28-32` |
| 正则越多越慢，卡到输入框打不出字 | 正则 `Pattern` **每次重新编译**，一条 2 万字的规则 × 全部消息 × 每 80ms 一次 | `stcore/RegexUtil.kt:54`（无 Pattern 缓存） |
| 点发送后要等 1~3 秒才出第一个字 | `assemblePrompt` 每次全量跑：世界书全条目扫描 + 宏 + 正则 + token 逐字符计数 | `src/engine/assembler.ts:35-214`、`src/bridge/generateService.ts:193-262` |
| 生成时整机发烫 | WebView `@JavascriptInterface` 是**同步 IPC**，Java 侧处理慢会反向堵住 renderer 的流式输出 | `chat/GenBridge.kt`、`NativeBridge.java` |

关于「单线程」的事实澄清（避免以后优化错方向）：

- Android 8+ 的 WebView 默认是**独立 renderer 进程**，JS 长任务**不直接**占 App 的 UI 线程；
- 但 `@JavascriptInterface` 调用是**同步跨进程**：Java 方法不返回，JS 就停住。所以原生侧 `render()` 越慢，流式越"卡壳"；
- 引擎 WebView 只有 1 个（`MainActivity` 里 1dp 透明，见 `MainActivity.java:195-209`），这点是好的，不要动；
- 真正要治的是：**原生全量重算** + **N 个气泡 WebView** + **无 Pattern 缓存**。

所以本方案的重点排序是：**原生渲染管线（收益 70%）> 卡片位图化（收益 20%）> Web 侧组装下沉（收益 10%）**。

## 1. 设计目标（可量化）

| 指标 | 现状（估算） | 目标 |
| --- | --- | --- |
| 打开 200 轮会话 | 1.5~4 s（全量跑正则） | < 400 ms 首屏，< 1.2 s 全量 |
| 流式期间主线程单帧 | 30~200 ms（全量重算） | < 8 ms，掉帧率 < 5% |
| 流式片段处理耗时 | O(全部消息 × 规则) | O(1)，< 2 ms |
| 同屏 WebView 实例 | 可见条数（3~8 个） | 0（默认）或 ≤ 2（开启实时模式） |
| 聊天页常驻内存 | 150~400 MB | < 120 MB（不含图片） |
| 发送 → 首字 | 1~3 s | < 800 ms（P4 后） |
| 自动摘要 | 无 | 后台 < 8 s，零阻塞，失败静默重试 1 次 |

## 2. 总体架构：四层 + 一条冷热分界线

```
┌──────────────────────────────────────────────────────────────┐
│ L3 视图层                                                     │
│   TextView(普通消息, 可选中)  │  ImageView(卡片位图)            │
│   流式气泡(单条 TextView)     │  卡片查看器(全屏单例 WebView)     │
└───────────────▲──────────────────────────▲───────────────────┘
                │ ChatItem(含 plain/html/height/cardPath)
┌───────────────┴──────────────────────────┴───────────────────┐
│ L2 渲染编排层  RenderPipeline（新）                            │
│   ├ 静态管线：内容定稿 → 跑全量正则/宏 → 产出 plain+html → 缓存  │
│   ├ 流式管线：只在"未定稿的尾巴"上跑轻量清洗（<2ms）             │
│   └ 卡片管线：html → 离屏 WebView → WebP 位图 → 磁盘            │
└───────────────▲──────────────────────────▲───────────────────┘
                │ RenderKey(内容哈希+配置指纹)
┌───────────────┴──────────────────────────┴───────────────────┐
│ L1 缓存层  RenderCache（新）                                   │
│   内存 LRU(64 条)  →  SQLite(render_cache 表)  →  磁盘位图目录   │
└───────────────▲──────────────────────────────────────────────┘
                │
┌───────────────┴──────────────────────────────────────────────┐
│ L0 数据层  SessionDoc（已有，原生权威）                        │
│   actions / variants / sceneDescription / summaries(新增)      │
└──────────────────────────────────────────────────────────────┘
```

**冷热分界线**：一条消息"内容定稿"之后，渲染结果就是纯函数的输出，永不重算（除非配置或外观变化）。只有"正在生成的那一条"在热区。

## 3. 静态 / 动态 的判定规则（这是整个方案的地基）

| 类型 | 典型内容 | 何时重算 | 产物存放 |
| --- | --- | --- | --- |
| **静态** | 历史 AI 回复、用户消息、开场白、导入的 jsonl | 内容变 / 正则变 / 字体字号变 | 内存 LRU + SQLite |
| **半静态（变量驱动）** | 状态栏、好感度面板、背包、日期卡片 | 变量表变（有依赖索引才重算） | 同上 + 变量依赖索引 |
| **动态（流式）** | 正在生成的那一条 | 每 120 ms 合并一次 | 不缓存 |
| **一次性** | 系统提示、error 占位 | 配置变 | 不缓存 |

判定实现（不靠人工标注，靠特征）：

```kotlin
// 一条消息属于哪类，由"内容 + 配置"推出来，不落库
enum class RenderClass { STATIC, VAR_DRIVEN, STREAMING, EPHEMERAL }

fun classify(text: String, scripts: List<RawScript>, isGenerating: Boolean): RenderClass {
    if (isGenerating) return RenderClass.STREAMING
    // 卡片特征：自带样式/结构，或残留只读变量宏
    val looksCard = text.contains("<style", true) ||
        Regex("<(div|details|table|section|article)\\b", RegexOption.IGNORE_CASE).containsMatchIn(text)
    val usesVar = VAR_MACRO.containsMatchIn(text)          // \{\{(getvar|getglobalvar)::[^}]+\}\}
    return when {
        usesVar && looksCard -> RenderClass.VAR_DRIVEN
        else -> RenderClass.STATIC
    }
}
```

`VAR_DRIVEN` 的消息额外记录它读了哪些变量名 → 建立 `变量名 → Set<actionId>` 反向索引。变量变化时只重渲染索引命中的那几条，而不是全表。

## 4. 模块一：渲染缓存（收益最大、风险最低，先做）

### 4.1 缓存键

```kotlin
/** 渲染的完整输入指纹：任一变化都必须重算。 */
data class RenderKey(
    val actionId: String,
    val contentHash: Long,     // 正文 + 图片 id 列表 的哈希（SHA-256 前 8 字节，别用 hashCode 防碰撞）
    val cfgVersion: Int,       // 正则/宏上下文/变量表 的版本号（配置加载时 +1）
    val lookVersion: Int,      // 字体/字号/行距/颜色/气泡宽度 的版本号
    val depth: Int,            // 仅当存在"深度敏感脚本"时参与，否则固定 -1
)
```

要点：

- `cfgVersion` 用「配置内容哈希」而不是时间戳：用户没改配置时，重开 App 也能命中；
- `depth` 谨慎用：`depth = 总数-1-i`，追加一条会让**所有旧消息 depth+1**，缓存全失效。所以只有存在 `minDepth/maxDepth` 脚本时才把 depth 纳入 key，且把 depth 量化成 bucket（0..9 / 10+），减少抖动；
- **绝不能**把「当前时间」放进 key（好看的时间戳卡片会永远不命中，反而更慢）。

### 4.2 三级缓存

```kotlin
interface RenderCache {
    fun get(key: RenderKey): RenderedMsg?
    fun put(key: RenderKey, msg: RenderedMsg)
    fun invalidateSession(sessionId: String)   // 删会话/导入/迁移时
    fun invalidateConfig()                     // 正则/宏/变量变 → 全清 cfg 维
    fun invalidateLook()                       // 字体字号变 → 只清 look 维
}
```

| 级 | 存储 | 容量 | 淘汰 |
| --- | --- | --- | --- |
| L1 内存 | `LruCache<RenderKey, RenderedMsg>` | 64 条 或 12 MB | 按条数 |
| L2 SQLite | `render_cache(session_id, action_id, key_hash, plain, html, height_px, updated_at)` | 每会话 ≤ 2000 行 | 会话删除时级联；全局 64 MB 按 updated_at |
| L3 位图 | `files/data/cards/<keyHash>.webp` | 128 MB | 按 mtime LRU，启动时清一次 |

为什么用 SQLite 而不是每会话一个 JSON：产物是可变长 HTML（单条可达 50 KB），200 条 = 10 MB，多文件会产生上千小文件、写放大严重。SQLite 单表 + WAL 最稳，且**不引第三方依赖**（`android.database.sqlite` 即可，项目现在没有 Room，别为此加）。

缓存可随时删，删了只是慢一次 —— 这条要写进 README，避免以后把它当权威数据。

### 4.3 打开会话的预热

```kotlin
// ChatController.open() 之后，后台按"从最新往前"预热
io.execute {
    val order = doc.actions.indices.reversed().take(30)   // 首屏附近 30 轮
    for (i in order) buildItemCached(doc.actions[i])
}
```

从最新往前，是因为打开会话默认停在底部。用户往上翻时再按需补。

## 5. 模块二：增量渲染（治「每 80ms 全量重算」）

### 5.1 现状问题

```kotlin
// ChatController.kt:428
override fun onGenDelta(text: String) {
    genText = text
    render(false)          // ← 这里每次都重建整个会话，跑全部正则
}
```

200 轮会话 + 20 条正则 × 每条 2 万字 = 每次 delta 几十到几百毫秒，而 delta 每 80ms 来一次 → 永久饱和，队列越积越长，用户看到"打字卡、滚不动"。

### 5.2 改法：只重算变化项

```kotlin
/**
 * @param changed null = 全量（打开会话/换配置）；非 null = 只重算这些 actionId
 * @param structural 结构是否变化（增删/排序）—— 只有结构变了才重算 depth 敏感项
 */
private fun render(changed: Set<String>? = null, structural: Boolean = false, scroll: Boolean = false)
```

流式路径：

```kotlin
override fun onGenDelta(text: String) {
    if (genId == null) return
    genText = text
    // 1) 只跑"热区"一条的轻量管线
    // 2) 用 payload 局部刷新，不 submitList 整个列表
    sink.onStreamingText(genActionId, lightRender(text))
}
```

```kotlin
// NativeChatActivity
override fun onStreamingText(actionId: String, text: String) {
    val pos = adapter.currentList.indexOfFirst { it.actionId == actionId }
    if (pos < 0) return
    adapter.patch(pos) { it.copy(content = text, streaming = true) }
    // patch() 内部：list[pos] = new; notifyItemChanged(pos, PAYLOAD_STREAM)
    if (stickToBottom) scrollToBottom()
}
```

`onBindViewHolder(holder, position, payloads)` 里对 `PAYLOAD_STREAM` **只做 `setText`**，不重建气泡 Drawable、不重载图片、不碰 meta 区 —— 这才是流式顺滑的关键。

节流也要加在原生侧：delta 合并到 **120 ms** 一次（web 侧 80ms 保留，原生再兜一层），保证 UI 每帧最多一次 setText。

### 5.3 结构变化的正确处理

| 操作 | 重算范围 |
| --- | --- |
| 发送新消息 | 只算新 action + 生成占位 |
| 生成完成 | 只算这一条（全量管线）+ 写缓存 |
| 编辑消息 | 只算这一条 |
| 删除/分支/切版本 | 结构变化 → 重算被删/被切的那条及其后（depth 敏感时才扩散） |
| 改正则/预设/变量 | `cfgVersion+1` → 全量（后台，可显示"正在应用美化…"） |
| 改字体/字号/颜色 | `lookVersion+1` → 只重 bind，**卡片位图需要重生成** |

## 6. 模块三：流式管线（只做"不会后悔"的事）

流式期间**不跑正则、不跑 HTML**。原因：正则可能跨整篇（比如整篇包 `<style>`），增量跑一定出偏差，最后 done 时再纠正会出现"文字跳变"。这是 ST 生态里公认的做法：流式给纯文本，定稿再美化。

```kotlin
object StreamPipeline {
    /**
     * 流式轻量渲染：< 2ms，只做三件事
     *  1. 思考块截断（用户开了"隐藏思维链"时）
     *  2. 剥图片标记（[[IMG: ...]] 不显示成乱码）
     *  3. 收尾补光标 ▍
     *
     * ★ 刻意不跑正则：正则可能在流式中途匹配到半截标签，产出"半个 <div>"，
     *   既难看又会污染缓存。定稿后 onGenDone 再跑全量，一次到位。
     */
    fun render(text: String, hideReasoning: Boolean, cutMarker: String?): String
}
```

如果要"流式也美化"（用户可开），只允许**无跨段风险**的脚本进入热区：`findRegex` 不含 `[\s\S]`/`^`/`$`/`<style` 且不带 `g` 之外的整篇标记。这个判断写在 `DisplayConfig` 加载时，每个脚本打一个 `safeForStream: Boolean`。默认**关闭**流式美化（省电、省心）。

## 7. 模块四：正则与宏的引擎级优化

### 7.1 Pattern 缓存（一行改动级别的收益）

```kotlin
// stcore/RegexUtil.kt
private val patternCache = object : LruCache<String, Pattern>(512) { ... }  // 手写 LinkedHashMap 即可，stcore 不依赖 Android

fun compile(src: String, flags: Int): Pattern =
    patternCache.getOrPut("$flags|$src") { Pattern.compile(src, flags) }
```

配套：`refreshDisplayConfig()` 之后调一次 `precompile(scripts)`，把编译成本挪到"打开会话时的一次 30~60ms 后台"，而不是"每次 delta 的 12 次/秒"。

### 7.2 脚本预筛

每轮对每条消息都遍历全部脚本是浪费。加载配置时按 `placement` 分桶，并把 `minDepth/maxDepth` 预排序：

```kotlin
class ScriptSet(raw: List<RawScript>) {
    val aiOnly: List<Compiled>       // placement 含 AI_OUTPUT
    val depthSensitive: Boolean      // 存在 minDepth/maxDepth 的脚本
    fun forMessage(depth: Int): List<Compiled>  // 深度过滤在桶内二分
}
```

### 7.3 宏替换的短路

`transformForDisplayRich` 里先判 `text.contains("{{")`，不含就直接跳过宏展开与变量读取。现有多数消息不含宏，这一条能再省 30%。

## 8. 模块五：卡片位图化（治「N 个 WebView」）

### 8.1 现状

`item_chat_message.xml` 里 `msg_html` 是一个真 WebView，而且是**布局里的固定控件** —— 意味着 RecyclerView 每 inflate 一个 ViewHolder 就创建一个 WebView，不管这条消息是不是卡片、是不是 `GONE`。默认复用池 + 同屏可见，实际同时存活 8~12 个 WebView。每个 WebView 有独立渲染上下文（约 15~40 MB），滚动时还要 `loadData` + `evaluateJavascript` 重新量高度。这就是"一顿一顿"和"内存飙高"的直接原因。

### 8.2 方案：静态卡片 → WebP 位图；动态卡片 → 节流重绘

```
html 定稿
   │
   ├─ 普通 Markdown ──────────────► TextView（可选中、可复制）
   │
   └─ 卡片型 HTML
         │  离屏渲染（单例 1dp WebView，复刻引擎 WebView 的做法）
         ▼
      measure 内容高度 → draw 到 Bitmap → 压缩（API 30+ 用 WebP，以下用 JPEG q90）
         │
         ▼
      files/data/cards/<keyHash>.webp  +  height_px 存 SQLite
         │
         ▼
      列表里是 ImageView（固定高度，零 WebView）
```

为什么这样最优：

| 维度 | 每气泡 WebView | 位图方案 |
| --- | --- | --- |
| 同屏 WebView 数 | 3~8 | 0 |
| 内存 | 每条约 15~40 MB | 每张 0.5~2.5 MB（按屏宽解码后；磁盘文件约 30~200 KB） |
| 滚动帧率 | 30~50 fps | 55~60 fps |
| 高度稳定 | 需异步 measure，会跳 | 已知，不跳 |
| 文本可选中 | 是 | 否（长按菜单给"复制原文/查看卡片"） |
| 脚本动画 | 是 | 否（按帧重绘，默认关闭） |

**代价与补偿**：

- 不能选中文本 → 长按气泡弹原生菜单："复制原文 / 查看卡片"；"查看卡片"打开全屏单例 WebView（`CardViewerActivity`），里面可以选中、可以跑脚本；
- 动画卡片（CSS animation）→ 默认只取首帧；设置里可开"动态卡片"，按 1s/2s 重绘位图（省电模式自动关）；
- 图片加载：离屏 WebView 需要等图片 decode 完再截图 → `onPageFinished` + `postDelayed(300)` 双保险（现有 `bindHtml` 已有类似逻辑，可直接复用）。

### 8.3 离屏渲染器

```kotlin
/**
 * 卡片渲染器：全局单例，1 个 1dp WebView，串行渲染。
 *
 * 为什么必须"挂在窗口上"：部分机型对未 attach 的 WebView 不做 layout，
 * draw 出来是空白。复刻 MainActivity.attachEngineTo() 的做法，挂 1x1。
 */
object CardRenderer {
    fun render(html: String, widthPx: Int, cfg: CardStyle, onDone: (CardResult) -> Unit)
    // 内部：loadDataWithBaseURL → onPageFinished → measure → draw → 压缩 → 落盘
    // 串行队列，带 800ms 超时；超时降级为"纯文本气泡 + 提示"
}
```

渲染宽度必须固定为气泡宽度（`bubbleMaxWidthPx`），所以**改气泡宽度 = 位图全失效**，这点要写进设置页提示。

### 8.4 渲染开关（用户要的"单独开关"）

新增设置组「渲染与性能」：

| 开关 | 默认 | 说明 |
| --- | --- | --- |
| 美化渲染 | 开 | 关掉则所有消息走纯文本（最快、最省电） |
| 卡片渲染方式 | 位图 | `位图`（推荐，滚动最顺） / `实时网页`（可选中、可动画，费内存） |
| 流式美化 | 关 | 开启后流式过程中也跑安全正则（更炫，稍费电） |
| 动态卡片刷新 | 关 | 开：1s / 2s / 5s 重绘（状态栏类卡片才需要） |
| 允许卡片执行脚本 | 关 | 高风险，默认关；开启时在隔离渲染器里跑，不给任何 bridge |

每个开关下面用一行小字写清代价（"更顺但不可选中文本"这类），不要让用户猜。

## 9. 模块六：把"静态的东西"真正落到安卓侧

现状：会话正文已在原生（`SessionDoc`），但**渲染产物**没有；每次打开都要重算。补三样：

1. **渲染缓存表**（见 §4.2）—— 已定稿消息的 plain/html/height；
2. **卡片位图目录**（见 §8.2）—— 视觉成品直接落盘，冷启动秒开；
3. **摘要块**（见 §10）—— 压缩后的上下文，存进 `SessionDoc.nativeSummaries`。

三者都是"可重建的派生物"，删掉不影响数据正确性。这一点要在 README 里写死，防止以后有人拿缓存当数据源。

## 10. 模块七：自动摘要（原生生成，只借 web 解析预设）

### 10.1 语义定义（先说清"条"是什么）

用「轮」（一个 `SessionAction` = 用户一句 + AI 一句）计数，避免 user/ai 两条算两次的歧义。设置页文案写「轮」。

```
actions:  [0]...[7] [8][9]  ← 原文
           └已摘要┘ └保留┘
触发：未摘要轮数 ≥ summaryEvery(10)
取数：从最早未摘要处取 summaryTake(8) 轮做摘要
```

用户提的「每 10 条总结 8 条」正好是这个模型：触发阈值 10，单次取 8，留 2 条给下一轮滚入。

★ 不再单独设 `keepRecent`：`everyCount - takeCount` 的差值天然就是"最近几条留原文"。多一个参数只会让用户困惑（"我设 10 条，怎么 14 条才总结"）。

### 10.2 数据结构（向后兼容，绝不动 web 字段）

```kotlin
// stcore/session/SessionDoc.kt 追加
data class SummaryBlock(
    val id: String = "",              // "sum-<时间戳>"
    val text: String = "",            // 摘要正文（≤ 400 字）
    val fromIndex: Int = 0,           // 覆盖 action 下标（含）
    val toIndex: Int = 0,             // 覆盖 action 下标（含）
    val toActionId: String = "",      // 锚点，编辑/删除后用来校验是否错位
    val createdAt: Long = 0L,
    val model: String = "",           // 用的哪个模型，便于排错
    val raw: String? = null,
)
```

写入 `SessionDoc` 的 JSON 时用 **`nativeSummaries`** 这个带前缀的键（和 `nativeLocalPath` 同一套约定），web 读到会忽略，写回也不会抹掉（`raw` 兜底机制已经保证这点）。

### 10.3 触发与执行

```
onGenDone / onGenStopped / onGenError(有部分正文)
        │
        ▼
SummaryScheduler.maybeSchedule(sessionId)   // 只做判断，不做事
        │ 未摘要轮数 >= N 且 无正在跑的摘要
        ▼
summaryQueue（单线程，串行）→ SummaryService.run()
        │
        ├─ 取 [from, from+take) 轮原文（剥图、剥 HTML）
        ├─ 拼 prompt → OkHttp 直连（非流式，max_tokens 400, temp 0.3）
        ├─ 成功：写 SummaryBlock → 落盘 → 通知界面（可选"已生成摘要"轻提示）
        └─ 失败：静默重试 1 次（指数退避 2s）；再失败就跳过，等下次触发
```

为什么**不用** web 的 generate 通道：那条路会触发世界书、注入角色卡、跑正则、按 token 裁剪，摘要会被"角色扮演化"，而且会占用生成状态机（用户可能正在等回复）。

但它**要用预设** —— 写作规则、格式要求、前置语决定了摘要长什么样。所以实际做法是：

```
原生 SummaryService
  ├─ EngineBridge.fetchJson("exportSummaryPreset", presetId)   ← 同步取值，只要预设
  │     web 侧 collectPresetMessages()：按 prompt_order 排序、跳过关闭项、
  │     清空角色卡/世界书宏（只留 {{char}}/{{user}} 名字）、不截断
  ├─ 拼请求：预设原文 + 系统指令(+自定义) + 上下文(已有提要 + 本次原文)
  └─ OkHttp 直连（非流式，temp 0.3，max_tokens 按摘要字数算）
```

一句话：**借 web 的预设解析能力，不借它的组装管线**。API 配置复用 `ConnectionStore.llmRuntime()`，不新增配置面。

### 10.4 摘要请求（实际结构）

```
messages = [
  ...预设条目,                       ← 全量、不截断；角色卡/世界书宏已清空
  { system: 内置压缩指令 + 用户自定义 },
  { user:  已有前情提要 + 本次需要压缩的对话 },
]
```

要点：

- **预设放在最前、任务指令放在最后**：后置指令权重更高，能压过预设里"扮演"的倾向；
- **用户自定义提示词追加**在内置指令之后，不替换内置规则 —— 内置那几条（保留人物/承诺/冲突）是摘要不跑偏的底线；
- **原文不逐条截断**：以前每轮 `take(600)` 会把长回复的关键情节砍掉；现在只在总量 6 万字（约 3 万 token）时按"头 40% + 尾 60%"省略，正常 8 轮根本触发不到；
- **已有摘要一起带上**：滚动摘要必须承接前情，否则第 3 次摘要就丢了开头。生成后仍只落一条块（`fromIndex` 合并到最早起点），用户只需要编辑一处。

### 10.5 注入到上下文（关键：改在原生，web 不用动）

`SessionHistory.export()` 增加摘要支持：

```kotlin
fun export(doc: SessionDoc, uptoActionId: String? = null): List<PromptMessage> {
    val out = ArrayList<PromptMessage>()
    out += sceneDescription

    // 1) 摘要块：按时间顺序拼成一条，放在场景描述之后、原文之前
    //    角色用 system（可配置），明确标注"以下是前情提要"
    val summaries = doc.summaries.filter { it.toIndex < startIndex }
    if (summaries.isNotEmpty()) {
        out += PromptMessage(
            role = "system",
            content = "【前情提要（自动摘要，非当前场景）】\n" + summaries.joinToString("\n") { it.text }
        )
    }

    // 2) 摘要区间之后的原文（被摘要覆盖的轮次不再发送）
    for (i in firstRawIndex until end) { ... }
}
```

要点：

- **原文永远不删**，只是"不发给模型"。用户随时能回看、能关掉摘要恢复正常上下文；
- 摘要块 `role` 可配（默认 `system`；某些中转不支持多条 system 时可切 `assistant`）；
- 被摘要区间**不参与** web 的 token 裁剪（`_origin` 不是 `history`），所以不会出现"摘要刚压完又被裁掉"的荒谬情况；
- `uptoActionId` 落在摘要区间内（重新生成一条老消息）时，**回退到原文**：从该 action 所在轮开始的前 N 条不走摘要 —— 否则重新生成会看不到细节。

### 10.6 失效与一致性

| 事件 | 处理 |
| --- | --- |
| 用户在摘要区间内编辑/删除消息 | 校验 `toActionId` 是否还在原位；不在 → 该 `SummaryBlock` 标记 `stale`，下次触发时重算覆盖 |
| 切换版本（‹ ›） | 不影响摘要（摘要只覆盖已定稿文本；切版本会让对应轮重新进"未摘要"集合，可选重算） |
| 导入 jsonl / 分支会话 | 新会话无摘要，从头开始 |
| 用户关闭自动摘要 | 停止调度；已有摘要保留但**不注入**（设置页给"清除全部摘要"） |
| 会话被摘要后再删到很短 | 摘要越界 → 整体丢弃，回退原文 |

### 10.7 设置页（实际落地：设置首页 →「渲染与上下文」）

| 项 | 控件 | 默认 | 说明 |
| --- | --- | --- | --- |
| 启用自动摘要 | 开关 | 关（opt-in） | 关掉完全不影响现有行为 |
| 触发方式 | 按条数 / 按字数 | 按条数 | 长回复多时按字数更省钱 |
| 多久触发一次 | 数字弹窗 | 10 条 / 4000 字 | |
| 每次浓缩几条 | 数字弹窗 | 8 条 | 必须小于触发阈值（代码钳制） |
| 摘要字数上限 | 数字弹窗 | 400 字 | |
| 摘要带预设 | 开关 | **开** | 预设全量带；角色卡/世界书永远不带 |
| 自定义摘要提示词 | 编辑弹窗 | 空 | 追加在内置指令后 |

## 13. 坑清单（这一节比方案本身重要）

1. **缓存键漏了变量表** → 用户改了变量，界面还是旧值。`cfgVersion` 必须包含「变量表内容哈希」，不能只用"配置对象引用变了"。
2. **depth 进 key 导致全量失效** → 每发一条消息，200 条缓存全废，比不做还慢。只有 `depthSensitive` 时才纳入，且量化。
3. **流式跑正则** → 中途匹配到半个标签，界面出现"半个 `<div>`"，定稿后又跳变。流式只做轻管线。
4. **`notifyDataSetChanged` 处理流式** → 每次重绑全部可见项、重建气泡 Drawable、重载图片。必须 `notifyItemChanged(pos, payload)`。
5. **WebView 复用不清状态** → 上一条的高度/滚动/tag 残留，出现"气泡下方一大片空白"（现有 `bindHtml` 的注释里已经踩过一次）。池化后每次 acquire 必须 reset：`tag=null`、高度清 0、`loadUrl("about:blank")` 可选。
6. **离屏 WebView 未 attach 就 draw** → 部分机型白图。必须挂 1dp 到窗口，或直接在 `CardViewerActivity` 的 decor 上挂。
7. **位图没算 density** → 截出来糊成一片。WebView 的 CSS px ≠ 设备 px，`× density`（现有代码 `ChatAdapter.kt:275` 已有先例）。
8. **改字号/气泡宽度不清位图** → 卡片还是旧字号，文字和气泡对不上。`lookVersion` 变时必须清 `cards/` 目录。
9. **摘要注入位置错** → 把摘要塞在 system 预设中间，模型把它当指令执行。必须放在"预设块之后、历史之前"，并用明确的前缀标注"非当前场景"。
10. **摘要越界** → 用户删了消息，`toIndex` 指向不存在的轮次。所有读取必须 `coerceIn` + 校验 `toActionId`，不一致就丢弃该摘要。
11. **缓存当数据源** → 有人图省事从 `render_cache` 读正文。绝对禁止：缓存可随时清空，`SessionDoc` 才是唯一权威。
12. **P4 双实现漂移** → 原生 assembler 和 web assembler 各跑一套，正则/宏语义差一点就"同一句话两个结果"。P4 若做，必须用同一批 fixture 做对照测试（stcore 已有单测基础）。

## 15. 明确不做的事（防过度设计）

1. 不引 Room / 不引 kotlinx-serialization / 不引第三方图片库 —— 现有依赖够用；

### 17.3 这一轮踩到的坑

1. **预设 ≠ 角色卡**。第一版把"带预设"实现成了"带角色卡设定摘要"，方向错了。正确做法是：预设条目全量带，只把角色卡/世界书宏替换为空 —— 整条删掉会把回复规则一起删掉。
2. **不要加 `keepRecent`**。阈值 10、取 8 的差值已经保护了最近两条；再加一个参数只会让触发点漂移。
3. **摘要要承接前情**。只传本次 8 条，第 3 次摘要就丢掉开头；必须把已有提要一起发给模型，并合并成一条块。
4. **`val text` 遮蔽 `TextView.text`**。Kotlin `apply` 块里给 `text` 赋值会解析到外层局部变量，报 "'val' cannot be reassigned"；用 `setText()` 或改局部变量名。
5. **`SessionHistory` 顺序**：摘要放在场景描述之前。场景是"开场白"，摘要交代"之前发生了什么"，反了会让模型把提要当成开场。

### 17.4 仍需真机确认

- 卡片位图在真实机型上的清晰度与滚动表现（WebP 质量 90、宽度 = 气泡内容宽）；
- 摘要请求在用户的中转上是否接受"多条 system + 前置预设"（个别网关只允许一条 system → 设置里把 `role` 切成 assistant，目前未暴露 UI）；
- 长会话（200+ 轮）打开时的首帧与内存曲线。
