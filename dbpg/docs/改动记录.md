## 0. 一句话总览

网页仍是「引擎」，原生是「外壳 + 渲染 + 网络 + 存储」。

| 能力 | 谁来干 | 说明 |
| --- | --- | --- |
| 生成 / 会话 / 预设 / 正则 / 世界书 / 变量 | 网页（ST 兼容层） | 原生只读快照，不复制引擎，避免两套逻辑漂移 |
| 消息渲染、长按复制、滑动 | 原生（RecyclerView + Spannable） | 顺滑、不超框、不横滑 |
| 生图请求与落盘 | 原生（OkHttp + ZIP 解压） | 无 CORS、长超时、支持局域网/中转站 |
| 角色卡浏览与导入 | 原生（文件扫描 + PNG 卡解析） | 点击后交回网页建档，格式仍是 ST 的 |
| 外观（字号/行距/字体/颜色/气泡/背景） | 原生（SharedPreferences） | 只影响原生 UI，不动网页数据 |

## 0.5 边界速查：只有引擎，没有界面（2026-11-08 更新）

**仓库里只有一套界面：原生。** 网页界面（Vue / router / views / components）
已经物理删除，`src/` 只剩引擎。

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 界面 | `dbpg/app/src/main/java/...` + `res/` | 所有页面、列表、气泡、设置 |
| 引擎 | `src/native/main.ts` 入口 + `src/{store,engine,bridge,lib}` | ST 兼容、宏、正则、提示词组装 |
| 产物 | `native.html` → `dist/` → `assets/www/` | 单入口、无 Vue、无路由、无样式 |

**规则**

- 改界面 → 原生 `app/src/main/...`
- 改 ST 兼容 / 生成 / 资产 → `src/engine`、`src/bridge`、`src/stores`
- 想调试引擎 → `npm run dev`，浏览器开 `/native.html`（没有界面，只有 console 和 `__dhpApi`）

**为什么删**：低端机不必再解析 400KB+ 界面代码；更实际的理由是两套 UI 并存的后果 ——
网页改了、App 没改（预设改名入口就是这么漏的）。曾经的错误：字体颜色 / 字体型号
加到了 `src/views/Settings.vue`，而 App 根本不出那个页面。

> 需要找回旧界面：`git log --diff-filter=D -- src/views` 找到删除提交，
> `git checkout <commit>^ -- src/views`。不建议 —— 那等于把漂移重新引进来。

- 纯 Kotlin 解析：`**粗体**`、`*斜体*`、`` `代码` ``、`~~删除线~~`、`[文字](链接)`、裸链接、少量 HTML 归一化。

### 1.2 Spannable 渲染 `app/richtext/RichTextRenderer.kt`
- 把上面那份纯数据映射成 `SpannableString`。
- 关键修复（对应网页端「超框 / 左右滑动」）：
  - `setHorizontallyScrolling(false)` + `setSingleLine(false)` + `maxLines = MAX_VALUE`

### 1.3 列表 `app/chat/ChatAdapter.kt`

- 本轮新增：字号 / 行距 / 气泡宽度从 `AppearanceConfig` 读取，`updateConfig()` 热更新。

## 2. 生图（纯 Kotlin，绕开 CORS）

### 2.1 响应识别 `stcore/imagegen/ImagePayloadExtractor.kt`

**这是整个模块最关键的一段：中转站返回的东西什么形状都有。**

识别顺序（**先看字节，再看 Content-Type**，因为很多站把 ZIP 标成 `application/json`）：

1. **ZIP**：文件头 `50 4B 03 04` / `50 4B 05 06` / `50 4B 07 08`
   → `ZipInputStream` **内存解压**（不落临时文件），逐个 entry 按文件头/扩展名挑图片；
   → 单条目上限 40MB、总量上限 128MB（防 ZIP 炸弹）；
   → 坏包不崩，返回已成功读到的部分。
2. **直接图片**：魔数 `FF D8 FF`(jpg) / `89 50 4E 47`(png) / `RIFF....WEBP` / `GIF8`
3. **JSON**：`data[].b64_json`、`data[].url`、`data[].image`、顶层 `image`/`b64_json`/`images[]`
4. **data URL**：`data:image/png;base64,....`
5. **裸 base64**：直接解
6. 以上都不匹配 → 把响应文本原样回显（中转站报错信息对用户最有用）

配套：
- `Base64Codec.kt`：自研 base64（minSdk 24 用不了 `java.util.Base64`）
- `ImageFormat.kt`：魔数 → 扩展名/MIME
- `ImageRequestBuilder.kt`：拼 OpenAI 兼容请求体（size / n / model）

单测：`ImagePayloadTest`（17 个，含 ZIP、假 ZIP、坏包、各类 JSON）。

### 2.2 网络 `app/imagegen/HttpImageClient.kt`
- OkHttp，连接 30s / 读 300s / 整体 360s。
- HTTP + HTTPS 都行；`usesCleartextTraffic=true` 支持局域网 http（`192.168.x.x`）。
- 自定义 `baseUrl`，不经过 WebView，所以没有同源/CORS 限制。

### 2.3 存储 `app/imagegen/ImageStore.kt`
- 写 `filesDir/generated/`，返回 **本地绝对路径 + FileProvider Uri**。
- **绝不把 base64 传到 UI 层**（避免大字符串把列表卡死）。

### 2.4 桥
- JS：`AndroidNative.generateImage(requestJson, callbackId)`
- 原生回：`window.__dhpOnImageResult(callbackId, {ok, path, uri, error})`

## 4. 本轮（第三轮）新增

### 4.1 角色卡解析 `stcore/character/`
- `CharacterCard`：V2/V3 字段一一对应（snake_case），另有 `greetings`、`subtitle` 两个便捷属性。
- `CharacterCardParser`：
  - JSON：`spec + data` 优先，`spec` 写了但 `data` 缺失时自动退回顶层（野生卡常见）。
  - PNG：遍历 chunk，读 `tEXt` / `zTXt` / `iTXt` 里的 `chara` / `ccv3`，base64 解出 JSON；头像原图一并返回。
  - **所有失败返回 null，不抛异常**（第三方卡不能把列表拖崩）。
- 单测：`CharacterCardTest`（12 个，含手工构造的 PNG）。

### 4.2 角色库页 `app/character/`
- `CharacterRepository`：扫 `filesDir/characters/`，导入 `.png` / `.json`，重名自动加序号，单文件上限 32MB，`.charx` 明确报“请解压后导入”。
- `CharacterAdapter`：头像两步降采样（先读尺寸再按 128px 解），`RGB_565` 省内存。
- `CharacterListActivity`：列表 → 详情弹窗（描述 / 场景 / 标签 / 开场白）→ 「用它开聊」/「删除」。
- 「用它开聊」链路：原生把卡转成标准 V2 JSON → `window.__dhpApp.useCharacter(json)` → 网页 `importCharacter` 建档 → 建新会话 → 网页拉起原生聊天。
  **角色库仍然只有一份（网页 IndexedDB），原生不另存一份。**

### 4.3 外观设置 `app/appearance/`
- `AppearanceConfig(textSizeSp, lineSpacing, bubbleWidthPercent, hideReasoning)`，存 SharedPreferences。
- `SettingsActivity`：字号 12–24sp、行距 1.0–2.0、气泡宽度 60–94%、隐藏思维链开关；**改一下存一下**，带实时预览块。
- 聊天页 `onResume` 重新读取并 `adapter.updateConfig()`，返回即生效。

### 4.4 原生底部导航
- `MainActivity` 底部 56dp 导航：聊天（网页）/ 角色 / 生图 / 设置。
- WebView `bottomMargin = 56dp`（变矮而不是被遮），网页 `100vh` 仍等于可见区域。
- 只做入口跳转，不接管 WebView 内部路由。

## 4.5 第五轮：UI 原生化（会话 / 图片库 / 角色详情）

### 4.5.1 原生会话列表 `app/session/`
- 数据：`window.__dhpNative.getSessions()` 返回**字符串**（`evaluateJavascript` 只能序列化 JSON，
  返回对象会变成 `[object Object]`），原生用 `JSONTokener` 解一层再解析。
- `SessionBridge`：WebView 可能还没挂完，做 25 次 × 400ms 重试；取不到回空列表，不阻塞 UI。
- `SessionListActivity`：标题 + 消息数 + 相对时间 + 「当前」标记；点一条 → 网页 `openSession(id)`
  → 网页切换会话并拉起原生聊天。
- 会话的**增删改仍归网页**，原生列表是只读视图。

### 4.5.2 原生图片库 `app/gallery/`
- `GalleryRepository` 只扫 App 自己的两个目录：`getExternalFilesDir(PICTURES)`（生图落盘）、
  `cacheDir/chat_img`（聊天配图）。不递归、不碰外部存储、不申请权限。
- 3 列网格（`GridLayoutManager`）+ 自定义 `SquareImageView`（onMeasure 强制 1:1，避免拉伸）。
- 缩略图复用 `ImageLoader`（降采样 + LruCache），每格按屏宽/3 解码。
- 全屏查看 `ImageViewerActivity`：双指缩放（1–5x）、放大后拖动、双击 1x/2.5x 切换。
- 保存到相册走 `MediaStore`：Android 10+ 用 `RELATIVE_PATH` + `IS_PENDING` 免权限；
  Android 9 及以下才申请 `WRITE_EXTERNAL_STORAGE`（清单里 `maxSdkVersion=28`）。
- 入口：生图页顶栏「图片库」。

### 4.5.3 原生角色卡详情 `app/character/CharacterDetailActivity.kt`
- 取代原来的 `AlertDialog`：长描述可滚动、字段可长按复制、备用开场白可左右翻。
- 分段展示「角色描述 / 人格设定 / 场景 / 开场白」，空字段整段隐藏。
- 与列表页共用 `CharacterCardParser`，不缓存副本，避免两处内容不一致。

### 4.5.4 底部导航语义变化
- 「聊天」不再是空提示，改为打开原生会话列表；
- 「角色」「生图」「设置」不变。

## 6. 原生优先重构（第一批：数据层）

方向：WebView 只留「ST 兼容 + 生成」，其余全原生；桥从"每功能一套"收敛成两条。
完整设计见 `docs/原生优先架构方案.md`。

### 6.1 会话数据模型（stcore.session）
- `SessionDoc` / `SessionAction` / `ActionImage` / `MessageVariant`
- **未知字段原样保留**：每个对象带原始 JSON，写回时先铺 raw 再覆盖已知字段。
  web 以后加字段、老版本 App 保存，都不会把它抹掉。
- 时间戳兼容 数字 / 数字字符串 / ISO；坏 JSON 返回 null 不抛异常。

### 6.2 文件存储（stcore.session.SessionStore）
- `data/sessions/<id>.json` + `index.json`，一个会话一个文件
- 原子写：tmp → fsync → rename（断电不留半个文件）
- `rebuildIndex()` 可从文件重建索引；坏文件标「读取失败」但不拖垮列表
- id 白名单校验，挡 `../` 路径穿越

### 6.3 迁移通道
- web `dataExport.ts`：只读导出，**分页**（清单 → 单个会话 → 单个角色 → 单张图），
  避免几十 MB base64 一次性撑爆 WebView
- 原生 `MigrationCoordinator`：逐项请求 + 15s 超时保护；会话落 `SessionStore`，
  图片落 `AssetStore`（按 id 命名，可重复迁移不膨胀）
- 迁移页显示**重新扫目录**得出的条数，而不是计数器自报的数字

### 6.4 单测
- `SessionDocTest` 13 项：往返保真、未知字段保留、老数据、脏数据、时间格式
- `SessionStoreTest` 12 项：覆盖写、目录被删、索引损坏、坏文件隔离、非法 id、导入去重
- 全部：106 项，0 失败

### 6.5 已知限制
- 迁移是**单向只读复制**：网页侧数据不动，原生侧目前还没有界面读它（下一批接）
- `.charx`（zip 卡）仍未支持，迁移时按解析失败跳过

## 7. 第七轮：消息操作全原生 + 自动配图脱离 web

这一轮把「网页里才有的那五个功能」全部搬到原生：编辑 / 重新生成 / 分支 / 删除 /
版本切换 / 停止生成 / 点图放大 / 自动配图。同时把会话列表也切到原生文件。

### 7.1 单一数据源（本轮的架构决定）

```
原生（唯一写者）                     web（无状态，只算不发）
SessionDoc                          预设 / 世界书 / 正则 / 角色卡 / 变量
  actions[].user/ai  ← 当前版本       assemblePrompt() → chat/completions
  actions[].variants[] ← 历史
  actions[].images[]  ← 配图引用
        │
        └── SessionHistory.export() 只导出当前版本、剥掉 [[IMG:]]
                 └── __dhpGen.generate() ──► 流式回传全文
```

- **版本切换不发任何同步消息**：导出时只读 `user/ai`，`variants` 不出原生。
- **图片不进上下文**：`stripImageMarkers()` 在导出时剥掉占位符与内联 base64。
- **web 不写 store**：`generateService.ts` 里没有任何 `adventure.*()` 调用。

### 7.2 新增模块

| 文件 | 职责 |
| --- | --- |
| `stcore/session/SessionEditor.kt` | 编辑/重生成/切版本/分侧删除/分支，纯函数，21 项单测 |
| `stcore/session/SessionHistory.kt` | 会话 → 提示词消息（只当前版本、剥图），14 项单测 |
| `stcore/imagegen/AutoImageSupport.kt` | 自动配图的纯逻辑：限额、模板、提示词拼装、端点推导 |
| `app/chat/ChatController.kt` | doc ↔ ChatItem、所有消息操作、生成状态机 |
| `app/chat/GenBridge.kt` | 按 requestId 管理生成请求 + 4 个回调 + 配置快照 |
| `app/chat/DisplayConfig.kt` | 渲染配置解析（从 Activity 里抽出来，可复用） |
| `app/imagegen/AutoImageService.kt` | 原生自动配图：打标签 → 生图 → 落盘 → 回调 |
| `app/engine/EngineSettingsActivity.kt` | 只切「启用哪个」预设/角色/世界书 |
| `src/bridge/generateService.ts` | web 侧纯生成通道（无状态） |

### 7.3 关键实现细节

**流式节流**：web 侧 80ms 推一次**全文**（不是增量）。原生整段替换，
丢包也不会错位；同时避免每 token 一次 JS→Java 调用把主线程压住。

**停止一定要有终结回调**：用户可能刚点发送就点停止，此时 web 还卡在
变量写宏里、没有 AbortController 可掐。`generateService.stop()` 对这种情况
直接回 `onGenStopped`，原生才不会被"生成中"卡死。

**旧版本不会被第一次编辑吃掉**：`SessionEditor.seedCurrent()` 在第一次
修改前先把当前正文存进 `variants`，否则「‹ ›」永远翻不回初版。
空正文不 seed（会造出一个切过去全空的幽灵版本）。

**自动配图串行**：中转站普遍限制并发，一次回复通常 1~2 张，串行能保证
"第一张出来马上可见"，比并发一起等 30 秒体验好。单张失败换下一个候选端点，
不影响其他张。

**图放大**：`ChatAdapter` 给每张图加 `OnClickListener` → `ImageViewerActivity`
（双指缩放 / 拖动 / 双击 / 保存相册，已有）。

### 7.4 会话列表切原生

`SessionListActivity` 不再问网页要摘要，直接 `SessionRepo.list()` 读
`files/data/sessions/index.json`。没有数据时提供「导入」入口走一次性迁移。
原 `SessionBridge.kt`（web 摘要桥）已删除。

## 8. 黑屏修复 + 设置原生化（2026-11-07）

### 8.1 黑屏根因与修复

点「原生聊天」黑屏卡住，不是渲染慢，是主线程被撑爆：

1. 网页把整个会话快照（含每张图的 base64）序列化后跨桥传过去，
   原生在 onCreate **主线程**解析几 MB 的 JSON；
2. 紧接着又在主线程对每条消息跑整套 ST 显示变换（含 2.2 万字符的美化正则）。

修复（三处）：

- **快照瘦身**：`nativeBridge.ts` 的 getSnapshot 不再带图片 base64、
  不再带正则脚本表（原生迁移后有自己的 assets 存档）；
- **传 id 不传数据**：`AndroidNative.openNativeChatWithId(sessionId, snapshot)`
  原生只要有 id 就读本地会话文件，零解析；快照只作本地没有时的兜底；
- **重活出主线程**：ChatController 的 fromSnapshot / buildItems（跑正则渲染）
  移到后台执行，用序号防乱序，先出首帧再填内容。

另外加了 `CrashLogger.kt`：进程级崩溃堆栈落盘（files/crash/），
MainActivity 启动时读上一条打进 logcat —— 真机连不上 adb 时唯一能拿证据的地方。

### 8.2 当纯原生应用做

底部导航原生化并**分类对齐网页版**：冒险 / 资产 / 设置 / 生图
（MainActivity 常驻，WebView 缩成 1dp 透明引擎，GONE 会暂停 JS 定时器所以不能 GONE）。

设置页对齐网页版交互：

- `settings/SettingsHomeActivity`：接口配置 / 外观 / 引擎 / 图片库 / 数据迁移；
- `settings/ApiConfigActivity`：**输入 API 地址和密钥 → 拉取模型 → 选中即用**。

### 8.3 API 配置为什么要走 web store

生成请求是 web 引擎组装发出的，配置必须同源 —— 原生存一份、web 读一份必打架。
所以数据落在 apiConfig store，原生页通过引擎 WebView 上的 `window.__dhpApi` 读写：

| 方法 | 形式 | 说明 |
|---|---|---|
| `getConfig()` | 同步返回 JSON 串 | 当前地址/密钥/模型 + 运营商概览 |
| `saveConfig(json)` | 异步 | 结果回调 `AndroidNative.onApiResult` |
| `fetchModels(json)` | 异步 | 同上；复用 imageGen 的 fetchModels（兼容 /v1/models 各形态） |

坑：原生 evaluateJavascript 传参时，web 侧要的是 **JSON 字符串**
（内部 JSON.parse），必须用 `JSONObject.quote()` 包成 JS 字符串字面量，
直接内联对象字面量会被 JSON.parse 成 "[object Object]"。

地址/密钥用 `updateProvider`（运营商级同步，同一家全改），
选模型走「这家下已有就切、没有就 addModelToProvider」——与网页版行为一致。

## 10. 统一底板 + SVG 图标 + 换肤结构（2026-11-08）

### 10.1 问题：底板"有的实心、有的空心"

现状是**三套色值来源各写各的**：

| 来源 | 例子 | 谁在改它 |
| --- | --- | --- |
| XML drawable | `bg_card` 的 `#FFFFFF`、`bg_nav`、`bg_input`、`bg_menu_dialog` | 没人改 |
| 布局里硬编码 | `activity_native_chat` 顶栏 `android:background="#FFFFFFFF"` | 没人改 |
| 代码里 | `ChatAdapter` 的气泡色 | 按 `BubbleStyle` |

而"背景遮罩"（`bgDim`）只作用于 `BackdropDrawable` 里那张**盖在背景图上的遮罩**——
它连卡片都不碰。所以调滑块时，卡片、按钮、顶栏纹丝不动，看起来就像
"有些底板是实心的，有些是空心的"。

### 10.2 解法：一套 token + 一次递归

新增 `ThemeTokens`（`appearance/Theme.kt`）：

```
base        页面底色
dark        由 base 亮度算出（<128 即深色）
panel       面板底色（带 alpha）—— 卡片/按钮/顶栏/输入栏/弹窗都用它
panelSoft   次级面板（图标底、输入框）
accentSoft  淡主题色底（主按钮、选中 chip）
text/textDim/textFaint/icon   文字与图标三档
hairline    描边
onAccent    实心主题色底上的文字色
```

`ThemePalette.tokensOf(cfg)` 算出来，`UiBackdrop.apply()` → `View.applyTokens()`
**递归**套到每个 View：

- 背景判定用**亮度 + 饱和度**，不是枚举 drawable 名字：
  - 白/近白（亮度 ≥247、饱和 ≤26）→ `panel`
  - 顶白（≥236）→ `panelSoft`
  - 淡蓝（>200 且 b > r+15）→ `accentSoft`
  - 实心主题蓝 → `accent`，其上的文字改 `onAccent`
  - `ColorDrawable` 的纯白也一并处理（布局里直接写 `#FFFFFF` 的那种）
- 文字：按亮度分三档映射；蓝色系强调 → `accent`；危险红/成功绿**保留不改**。

**新设置项「底板不透明度」**（`panelOpacity` 0–100，默认 88）：
浅色主题下面板 = 白 + `25%~100%` 透明度（下限 25% 保证文字仍可读）；
深色主题 = 白 `5%~18%`（深色 UI 里浮层靠"比背景略亮"表达层级）。
拖到 100 就是纯实心白，往下拖背景图会从卡片后面透出来——
"实心/空心"从此是一个连续可调的量，而不是各写各的。

### 10.3 深色皮肤：文字自动翻白

`dark` 不是开关，是**底色亮度算出来的**。选了 `#15130F`，`tokensOf` 就把
`text/textDim/icon/panel` 全部换成深色系那套，布局里写死的 `#1A2230` 由
`mapTextColor` 按亮度映射过去。

> 这一条修正了 §9.2 末尾"别只改底色就以为有深色模式"的警告：
> 现在改底色**确实**会得到一套完整深色样式，因为文字/图标/描边/状态栏都跟着 token 走。

### 10.4 图标：emoji → VectorDrawable

新增 19 个 `res/drawable/ic_*.xml`（Lucide 风格描边，24dp viewport，线宽 1.7，
`strokeColor=#5A6B85`）：

- 导航：`ic_nav_adventure`（罗盘）/ `ic_nav_assets`（包裹）/ `ic_nav_settings`（滑杆）/ `ic_nav_image`（图片）
- 设置首页：`ic_llm` / `ic_palette` / `ic_sparkle` / `ic_eye` / `ic_folder` / `ic_gallery` / `ic_archive`
- 通用：`ic_chevron_left` / `ic_chevron_right` / `ic_plus` / `ic_close` / `ic_refresh` / `ic_tag`

替换点：底部导航 4 个 emoji、设置首页 8 个 emoji、8 处 `›` 箭头、
聊天输入栏 🎨（`TextView` → `ImageView`，代码类型同步改为 `View`）、
聊天顶栏 `‹`（同理）、消息下方"🎨 生图"改纯文字。

**图标必须带 `android:tint`**，否则 `UiBackdrop` 的 `tintIcon()` 拿不到
`imageTintList`，换主题色时图标不跟随。

### 10.5 换肤结构（留的尾巴）

`ThemePalette.STYLES`：云白 / 桃粉 / 黑金 / 墨蓝，每条只有 `(id, 名称, 底色, 主题色)`。
设置页「配色风格」选中即同时改底色+主题色。

以后加皮肤 = 在 `STYLES` 里加一行，**不用碰布局**。
想更进一步（字体、圆角、图标线宽也按风格走），在 `ThemeStyle` 上扩字段即可，
`tokensOf` 是唯一出口。

### 10.6 踩过的坑（重要）

1. **`GradientDrawable` 没有 `getStrokeWidth()`**，只有 `setStroke(int,int)`。
   读不到原宽度 → 没法"只换色不换粗细"；无条件 `setStroke` 会给本来没有描边的
   shape 硬加一圈框。所以描边保留 XML 原值，代码里不碰。
2. **Kotlin trailing lambda 永远绑到最后一个参数**。
   `onChange(apply, repaint=false)` 之后，`onChange { … }` 会报
   "No value passed for parameter 'apply'"——它把 lambda 当成 `repaint` 了。
   解决：保持单参函数 + 另写 `onChangeLive()`，不要给带默认值的方法加 trailing lambda 调用。
3. **RecyclerView 的 item 是滚动时现 inflate 的**，一次性递归覆盖不到，
   滚动出来的新卡片还是白的。`UiBackdrop.hookRecycler()` 给每个 RV 挂
   `OnChildAttachStateChangeListener`，新项进场按**当前** token 补色；
   用 `WeakHashMap` 防重复注册（`apply` 会被 onStart/onResume 调多次）。
4. **`postDelayed(500)` 补跑必须幂等**。第二轮递归时底板已是 panel 色、
   文字已是目标色，规则不再命中——所以不会越染越偏。加新规则时要保住这个性质。
5. **设置页预览块要打 `tag="dhp:keep-color"`**。它按用户选的字体色渲染，
   再被全局映射一次会把"酒红"改回墨黑，预览就不准了。
6. **聊天页的边界要单独划**：整页照常染色（顶栏/输入栏/菜单要统一），
   但 `ChatAdapter` 给每个气泡项打了 `tag="dhp:keep-color"`，
   `applyTokens` 见到这个 tag 就**连整棵子树**只套字体、不动颜色。
   否则用户选的"酒红/纯白"字会被映射回墨黑。
   另外聊天页在 `NO_BACKDROP` 里——背景由 `ChatBackground.applyTo(chat_root)` 设，
   这里再铺界面背景图会把它盖掉。

## 11. 渲染管线 + 卡片位图 + 自动摘要（2026-11-08，分支 `feat/render-pipeline`）

### 11.1 卡顿的真正原因（不是"WebView 单线程"）

| 现象 | 真因 | 位置 |
| --- | --- | --- |
| 长会话滚动掉帧 | 每个流式片段都 `render()` **全量重建**整个会话 | `ChatController.onGenDelta` |
| 内存高、滚动一顿一顿 | `item_chat_message.xml` **每条 item 一个 WebView**，滚回来就重载 | 同上布局 |
| 正则越多越慢 | `Pattern` 每次重新编译 | `stcore/RegexUtil.kt` |
| 发送后 1~3 秒才出字 | 组装时全量扫世界书/宏/正则/逐字符计 token | `assembler.ts` |

Android 8+ 的 WebView 是独立 renderer 进程，JS 不占 UI 线程；但
`@JavascriptInterface` 是**同步 IPC**，原生算得慢会把流式也堵住。

### 11.2 冷热分界：只让"正在生成的那一条"走热路径

- **冷区**：定稿消息只算一次，产物（plain / html / 高度 / 卡片位图）进
  `RenderCache`（内存 LRU → SQLite 单表 → 位图盘）。
- **热区**：只有 `genActionId` 那一条。走 `StreamPipeline.render()` 轻管线：
  截思考块、剥图片标记、补光标，**不跑正则**（半截文本会产出半个 `<div>`，
  定稿还会跳变）。
- delta 在 web 侧 80ms 已合并一次，原生再合并到 **120ms**，且只
  `sink.onStreamingText(actionId, text)`，不提交整表。

### 11.3 卡片：N 个 WebView → 1 张位图

- `CardRenderer`：单例离屏 WebView（挂在当前 Activity 上，detach 即销毁），
  按 `key = hash(actionId + html + lookHash + widthPx)` 渲染 → WebP(90) 落盘。
- `CardBitmaps`：解码 LRU 32MB，异步解码，给 ImageView 打 `tag=路径`
  防快速滚动错位。
- 列表里 `msg_html`（WebView）→ `msg_card`（ImageView）。
- 位图没就绪时**先显示纯文本**，同时请求渲染；完成后刷新这一条，
  高度用已知值占位，不跳。
- 点卡片 → `CardViewerActivity`（全屏单例 WebView，可选中、可跑脚本）。
- 渲染失败/超时的卡片进 `cardFailed`，永久降级纯文本，不反复堵队列。

### 11.4 自动摘要（这一轮的重点，也是返工过一次的地方）

**语义**：每 N 条（或 M 字）触发，压缩**最早**的 K 条；K < N，差值天然把最近几条留在原文。

**请求里有什么**（⚠ 第一版做错了，把"带预设"理解成"带角色卡"）：

```
[预设全部提示词]        ← 全量、不截断；角色卡/世界书宏清空，只留 {{char}}/{{user}} 名字
[内置压缩指令 + 用户自定义]
[已有前情提要 + 本次原文]
```

- **预设必须全量带**：砍一半等于预设失效。用户明确要求，也给了一个口子
  （「自定义摘要提示词」追加在内置指令之后）。
- **不带角色卡/世界书/正则**：摘要是压缩，不是扮演。做法不是"删掉引用角色卡的条目"
  （会把回复规则一起删），而是**把条目里的角色卡类宏替换为空**，
  再把"只剩 `角色设定：` 这种空壳行"删掉。
- **不逐条截断原文**：以前每轮 `take(600)` 会砍掉长回复的关键情节。
  现在只在总量 6 万字时按"头 40% + 尾 60%"省略。

**注入**：只改 `SessionHistory.export` 这一层，web 的 `assemblePrompt` 完全不知道
摘要存在（它收到的就是"一份变短了的干净历史"），所以不用改 web、也不会和
token 裁剪打架。顺序是 **摘要 → 场景描述 → 原文**。

**回退**：锚点 `toActionId` 对不上、下标越界、对早于摘要区间的消息重新生成，
一律退回原文 —— 张冠李戴比多花 token 严重。

**存储**：`SessionDoc.summaries`，JSON 键 `nativeSummaries`（空则删键）。
原文永不删除，只是不发给模型。

**交互**：聊天右上角 `chat_summary` → 查看 / 编辑 / 立即浓缩 / 清除。
有摘要时图标变主题蓝，任务中变淡。

## 13. 裁掉 web 界面：APK 只跑引擎（2026-11-08，分支 `feat/render-pipeline`）

### 13.1 为什么现在裁

低端机上，APK 里那套 Vue 界面是纯负担：要解析 700KB+ 的 JS、建一整棵 DOM、
跑路由与样式，而用户看到的每个页面都是原生的。更麻烦的是它带来「双 UI 漂移」——
网页改了、App 没改（预设改名入口就是这么漏掉的）。

裁掉之后，`src/` 的界面代码仍然保留、网页版仍可独立构建，只是**不进 APK**。

### 13.2 怎么裁（双入口，同一份引擎）

| 产物 | 入口 | 构建 | 内容 |
| --- | --- | --- | --- |
| APK | `native.html` → `src/native/main.ts` | `npm run build` → `dist/` | 只装桥与 store |
| 网页版 | ~~`index.html`~~ | ~~`npm run build`~~ | 已删除（见 §14） |

引擎入口做的事，顺序不能变：

1. `setActivePinia(createPinia())` —— 没有 Vue app，没人替我们 `use()`
2. `store.hydrate()` —— 必须早于任何 store 读取，否则读到默认值（表现为「预设空的」）
3. `assets / adventure / variables / apiConfig` 四个 `load()` 并行 ——
   少一个就会出现「建会话把旧会话覆盖掉」这类事故
4. 装三条桥：`__dhpNative`（先）→ `__dhpGen` → 迁移通道
5. 挂 `__dhpApp.useCharacter`
6. 只保留 `flush`，去掉 8 秒轮询（原生界面不看外部改动提示）

### 13.3 唯一的业务依赖：角色卡「用它开聊」

原生 `CharacterDetailActivity` 一直在调 `window.__dhpApp.useCharacter(json)`，
而那个函数原来写在 `Adventure.vue` 里 —— 不加载界面就断了。

现在抽到 `src/bridge/characterEntry.ts`：去重导入 → 设为当前角色 → 建会话 →
拉起原生聊天。网页版也改为调用同一份，不会两边各写一遍。

### 13.4 顺带削掉的耦合

- **资产页的结果白名单**：原来每加一条命令都要回 `onApiResult` 补一次名字，
  漏了就是「保存成功但列表不动」。改成「成功即重载，导入/导出单独处理」，
  新增命令零维护（这次的三条改名就是受害者）。
- **两个配置页**：`when` 末尾加 `else` 兜底 —— 忘了写分支也会刷新/报错，
  不再静默。
- **静态资源**：`public/` 里 1.1MB 背景图 + 128KB PWA 图标不进引擎产物，
  只补回 `tags/`（原生标签库直接读它）。

### 13.5 实测数据

| 项 | 裁前 | 裁后 |
| --- | --- | --- |
| APK | 5,982,623 B | 5,467,017 B（−515KB / −8.6%） |
| `assets/www` | 3.7MB | 2.5MB |
| 引擎 JS | 700KB+（多 chunk） | 397KB 单 chunk（gzip 128KB） |
| 启动路径 | Vue app + router + 全部依赖 | 一次 hydrate + 4 个 store load |

无头 Chromium 实测（直接跑 APK 里的 `assets/www/native.html`）：

- 状态 `引擎就绪`；`__dhpApi` / `__dhpGen.generate` / `__dhpApp.useCharacter` /
  `__dhpNative` 全部就位；`#app` 不存在（确认没有再挂 Vue）
- `__dhpApi.getAssets()` 返回合法结构
- 调 `__dhpApp.useCharacter(卡 JSON)` → 会话真的建出来了（3 条，含测试角色）

### 13.6 以后怎么改

- 加功能：只改原生 + 引擎命令，**不需要动 `src/views`**
- 想改网页版：`npm run dev` 照旧，改 `src/views` / `src/components`，不影响 APK
- 新增静态资源：放 `public/` 只会进网页版；APK 要用的必须显式加进
  `copyNativeStatic()`（目前只有 `tags/`）

### 13.7 顺手补的两处防护

**启动容错**：四个 store 的 `load()` 改成 `Promise.allSettled`。
某个盘里的数据坏了只影响那一类，引擎照常起来；`Promise.all` 会让整条链断掉，
表现是「App 完全不能用」，而真实原因可能只是一条脏数据。

**两个守卫脚本**（都能独立跑，不需要设备）：

- `scripts/_nativeonlycheck.mjs` —— 引擎入口不许 import `.vue`/router/样式；
  `bridge/stores/engine/lib` 不许反向 import 界面层；产物只允许一个入口脚本、
  不含背景图、JS 总量 < 600KB。防的是「以后悄悄把界面加回来」。
- `scripts/_bridgecontractcheck.mjs` —— 原生 `put("cmd", x)` 的每个 x，
  要么在 `generateService` 的 case 里，要么在 `ConnectionStore.LOCAL_COMMANDS`；
  本地命令还必须在 `apply` 里有实现分支。防的是「按钮点下去毫无反应」。

后者的输出里有一行值得记住：**21 条命令是本地/web 双实现**
（App 走 ConnectionStore，网页版走 store）。改这类命令的语义时要两边一起改，
脚本会一直提醒这个数字。

## 14. 点气泡分支 + 物理删除网页界面（2026-11-08，分支 `feat/render-pipeline`）

### 14.1 分支：点一下 AI 气泡就开新线

以前分支藏在 ⋯ 菜单里，是个"知道有才找得到"的功能。现在：

| 入口 | 行为 |
| --- | --- |
| **点 AI 气泡任意位置** | 复制到这一条（含）为止，新建会话并直接跳过去 |
| ⋯ 菜单 →「从这条分出新会话（含本条）」 | 同上（留着，给习惯用菜单的人） |

用户消息、系统提示、流式中的消息不响应 —— 这些位置分支没有意义，误触只会产生空会话。

**标题编号不是硬编码后缀**。规则在 `SessionEditor.branchSuffix()`：

- 先把标题尾部的 `（n）` / `(n)` 剥掉得到 base；
- 在**已有会话标题**里找 `base（n）` 的最大 n，+1。

所以「雨夜 → 雨夜（1）→ 雨夜（2）」，而不是「雨夜 · 分支 · 分支」那种越叠越长的字符串，
也不会因为删掉中间一条就撞号（取 max+1，不是数个数）。

**两个顺带修掉的真 bug**（都属于"分支一次，语义就变了"，但界面上看不出来）：

1. **资产绑定没复制**。预设 / 世界书 / 正则 / DNA 是按 sessionId 存在
   `session_bindings.json` 里的独立小文件，`branchFrom` 原来只复制会话 JSON，
   新会话读不到绑定就自动回落成"跟随全局" —— 表现是「分支出去预设就换了」，
   很难联想到是分支的锅。现在一并复制（仅当不是默认绑定时写，避免制造一堆空记录）。
2. **`raw` 被清空**。`branch()` 原来对每条消息做 `copy(id = ..., raw = null)`，
   而 `raw` 是未知字段的兜底（`speakerId`、ST 扩展、自定义元数据）。
   分支一次就把这些字段洗掉 —— 正好和 §4 里"raw 兜底是一切扩展的地基"相反。
   现在原样带走，`id` 在 `toJson()` 里覆盖，不会串号。

另外补了切会话保护：取标题列表是异步的，如果这期间用户已经切走，
分支照建但不把人拽回来（`if (doc?.id != d.id) return`）。

## 16. 预设顺序与「未激活提示词」（2026-11-08）

### 16.1 现象

导入 `Meowssiah_1.9.12.json` 后：

- 资产页里的子条目顺序，和 SillyTavern / Tavo 的主列表对不上；
- 感觉「有些条目被藏了」（ST 里明明有，这边像少了几条）。

拿真实文件对了一遍，数据本身没坏：

| 字段 | 条数 | 含义 |
| --- | --- | --- |
| `prompts[]` | 54 | **提示词库**，顺序是历史插入顺序，不代表发送顺序 |
| `prompt_order[100001].order[]` | 52 | **真正的发送顺序**，ST / Tavo 都按它显示 |

差的 2 条是 `【勿删】版本信息` 和 `SPreset配置`：它们不在排序表里，ST 把这类叫
**未激活提示词**，单独放在灰区，**本来就不参与生成**。所以不是丢了，是没分区。

### 16.2 根因：三处各读各的

| 位置 | 旧行为 | 后果 |
| --- | --- | --- |
| `assetsDetail` | 直接遍历 `prompts[]` | 显示顺序 = 插入顺序，和 ST 对不上 |
| `assetsDetail` 的 `enabled` | `prompts[].enabled && order[].enabled` 任一为 false 即关 | 比 ST 严格，出现「ST 里开着、这边显示关」 |
| `assembler` 阶段 1 | `listPromptEntries()`，默认 `includeUnordered: true` | 未激活但 `enabled=true` 的条目会被**悄悄发出去** |

最后一条是真 bug：ST 不发未激活项，我们发了，上下文就比 ST 多一截。

### 16.3 改法：一套规则，两个消费者

新增 `src/engine/presetOrder.ts`，只做一件事——把 ST 的排序语义讲清楚：

- **组选择**：`character_id === 100001` 的全局组优先，其次第一个非空组。兼容三种历史形态
  （`[{character_id, order}]` / `{ '100001': [...] }` / 纯字符串数组）。
- `listRankedPrompts(asset)`：有序区严格跟 `order[]`（`position` 从 1 递增），
  未激活区排在后面（`ordered=false`、`enabled` 恒为 false），与 Tavo 的灰区一致。
- `movePromptInOrder` / `activatePromptInOrder`：只改排序表，**绝不重排 `prompts[]`**。

消费方：

| 地方 | 用法 |
| --- | --- |
| `assembler` 阶段 1 | 只发 `ordered && enabled`；未激活数量写进 `warnings`，调试面板可见 |
| `assetsDetail` | 按 `position` 输出，带 `ordered` / `position` 给原生分区 |
| `summaryPreset` | 同样只取 `ordered`，摘要和真实上下文保持一套口径 |
| `syncPromptEnabled` | 只写当前生效组，不再把所有角色组一起改 |

新桥命令两条：

- `presetMovePrompt { presetId, identifier, dir }` —— 上下移一格；
- `presetActivatePrompt { presetId, identifier }` —— 未激活 → 追加到排序表末尾并启用。

### 16.4 原生界面

展开预设后分两区，顺序一眼可核对：

- **提示词 · 按 ST 发送顺序（52 条）**：`01` 序号 + `●/○` 状态点 + 名称 + `↑ ↓`；
- **未激活提示词 · 不参与生成（2 条）**：灰底、灰字，右侧「＋ 加入排序」。

两个刻意的取舍：

1. 未激活区**不给启停开关**。开关写不进 `prompt_order`，会出现「显示开了但没用」；
   要生效只能加入排序（对应 ST 里把它从灰区拖回主列表）。
2. 未激活条目的编辑对话框里，「启用」开关禁用并写明原因；保存时不回写 `enabled`。

只会更确信「丢了」。

## 17. `<details>` 折叠栏没有渲染（2026-11-08）

### 17.1 现象

AI 回复里的折叠栏（`小猫之神 - 折叠栏` + 内容）显示成两行普通文字，标题与正文还各带一段
行内代码底色 —— 看起来像"渲染没上去"。

### 17.2 根因：三条路径，没有一条能接 `<details>`

| 路径 | 旧行为 | 结果 |
| --- | --- | --- |
| 卡片位图 | 要求块级标签命中 **≥2 次**；`<details>` 开标签只命中 1 次（`</details>` 不匹配 `<details\b`） | 压根不触发 |
| 就算触发 | 卡片是离屏 WebView 画的**静态位图** | `<details>` 默认收起、点不动 → 内容消失 |
| 纯文本 | `stripHtmlNoise` 把 `<details>/<summary>` 换成换行 | 标题和正文平铺，没有层级 |

顺带解释了截图里的底色：预设常让模型用 `` `标题` `` 包 summary，行内代码样式
（`BackgroundColorSpan`）就落在那两行上。

### 17.3 改法：原生折叠块

新增 `stcore/richtext/FoldParser.kt`（纯 Kotlin，11 项单测），把富 HTML 切成两类块：

- `MsgBlock.Text` —— 普通段落，仍交给 `RichTextParser`
- `MsgBlock.Fold(title, body, open)` —— 折叠栏

覆盖的边界：`<details open>`、大小写混写、无 `<summary>`（标题用「详情」）、未闭合
（内容延续到末尾，不丢字）、嵌套（取最外层）、`<script>/<style>` 整块丢弃。

渲染在 `ChatAdapter`：气泡里新增 `msg_blocks` 容器，每块一个 View —

- 正文段：TextView（与 `msg_text` 同一套字号/行距/字体）
- 折叠块：淡主题色卡片（6% 底 + 22% 描边 + 左侧 3dp 竖条 + 标题 + `▾`），
  点击标题行展开/收起，箭头 160ms 旋转
- 展开状态按 `itemId#块序号` 存在 Adapter 里 —— 放 View 上会被 RecyclerView 复用串台
- 标题里的行内代码样式被剔掉：卡片本身已是淡色底，再叠一层会脏

### 17.4 路由：一条消息只走一条路

`ChatController.decideRender()` 三选一：

| 条件 | 走法 | 理由 |
| --- | --- | --- |
| 含 `<details>` 且不含 `<style>` | 原生折叠块 | 要可交互，位图做不到 |
| 像 HTML（含 `<style>` 或块级标签 ≥2） | 卡片位图 | 整页美化（表格/配色）只有 WebView 能还原 |
| 其余 | 单个 TextView | 最快、可选中复制 |

第二种会把 `<details>` 全部补上 `open`（`openAllDetails`）—— 位图里点不动，
不展开等于内容消失。这是"美观"和"可交互"之间的取舍：作者既然写了整页 CSS，
优先还原样式；纯折叠消息则优先交互。

### 17.5 缓存

`RenderCache` 的 `html` 列改成存**富 HTML**（不再只存卡片 HTML），命中时用
`decideRender` 重算路由。判定依赖 `appearance`，而它已经进 `lookHash`，
配置一改缓存自然失效，不会出现"改了设置还走旧渲染"。

### 17.6 验证

- `FoldParserTest` 11 项（含嵌套、未闭合、大写标签、无 summary、样式块剥离）；
- `:stcore:test` 全量 **210** 项通过；
- `:app:compileDebugKotlin`、`assembleDebug` 通过；
- `aapt2 dump resources` 确认 `msg_blocks` 进包，dex 中确认 `FoldParser` 已编译。

### 17.7 已知边界

- 流式生成期间仍走纯文本（避免半截 `<details>` 每帧重建卡片），结束后自动切成折叠；
- `.jsonl` 只读预览不带富 HTML，折叠仍显示为纯文本；
- 嵌套折叠只渲染最外层，内层标签在正文里被剥成普通文字。

## 18. 消息正文改用 WebView 真渲染（2026-11-08）

### 18.1 为什么推翻 §17

§17 用原生折叠块解决了 `<details>` —— 但**只解决这一种写法**。用户的原话是
「你这么针对性的改没用，因为那个正则千奇百怪的，显示还是要 web 引擎去渲染」。

对照真实预设看，正则产出的东西至少有这么几类：

| 形态 | 例子 | 原生 TextView / 原生折叠块 |
| --- | --- | --- |
| 折叠栏 | `<details><summary>` | §17 能处理 |
| 整页美化 | `<style>` + `<div class="card">` | 只能画位图（不可交互） |
| 表格 | `<table><tr><td>` | 完全不认，退化成竖排文字 |
| 自定义标签 | `<xy-statusbar>`、`<span class="hl">` | 当字面文字显示 |
| 内联样式 | `<font color>`、`style="..."` | 只能近似 |

也就是说：**原生侧不可能追完**。渲染这件事只有 WebView 能做对，
Tavo / Wivern / SillyClient 全都是这条路（Wivern 甚至是整页 WebView 跑 ST）。

### 18.2 结构：一个壳 + 三个资源

```
app/src/main/assets/msg/
  render.html      壳：只加载一次，之后靠 JS 换内容
  render.css       基础排版（details / table / blockquote / code / 列表…）
  render.js        marked 解析 + 高度回传 + 主题注入
  marked.min.js    Markdown 解析（35KB，MIT，ST 用的 showdown 同类）
```

**为什么是壳而不是每次 loadData**：列表滚动时 ViewHolder 反复 bind，
每条都拼一份 40KB 字符串重新 loadData，等于每次重建文档 + JS 上下文，
十几毫秒起步，滚动必掉帧。现在每个 WebView 只在创建时 `loadUrl` 一次，
之后 `evaluateJavascript("DHP.render(...)")`。

**为什么 Markdown 交给 marked**：角色扮演正文是 Markdown 和 HTML 混着用的
（`*动作*`、`**强调**`、`> 引用`、``` 代码块 ```，外面再套正则产出的标签）。
原来 WebView 路径直接 `htmlifyNewlines` 后插进 DOM，`*动作*` 就显示成字面星号。

### 18.3 判定：只排除 `<br>`

```kotlin
MARKUP_TAG = Regex("<([a-zA-Z][a-zA-Z0-9-]*)(\\s|/?>)")
hasMarkup = MARKUP_TAG.findAll(html).any { !it.value.startsWith("<br", ignoreCase = true) }
```

`<br>` 必须排除：`htmlifyNewlines` 会给**每条多行消息**插 `<br>`，
拿它当判据等于所有消息都走 WebView。

上一版是「`<style>` 或块级标签 ≥2 才算 HTML」，`<details>` 单开标签只命中
1 次，于是被判成普通文本 —— 这就是截图里折叠栏变成两行裸字的直接原因。

### 18.4 性能：把 WebView 数量压到可接受

| 手段 | 说明 |
| --- | --- |
| 只有含标记的消息才建 WebView | 纯文本占绝大多数，仍走 TextView（可选中复制、最快） |
| 回收池上限 2 | `setMaxRecycledViews(TYPE_HTML, 2)`，默认 5 会堆出十几个实例 |
| 内容指纹 | `长度 + hashCode`，重复 bind 直接返回，不重复解析 |
| 长度上限 20 万字符 | 超了退回纯文本（十万字经 IPC + marked 会按住主线程几百毫秒） |
| 流式期间不走 WebView | 半截 HTML 每帧重建 DOM 会抖，生成结束再切 |

### 18.5 高度与滚动

WebView 不支持 `wrap_content`，必须显式给高度：

- `render.js` 用 `ResizeObserver` 监听 `#m`，变化时 `DHPBridge.height(px * dpr)` 回传；
- `<details>` 的 `toggle` 不冒泡，但**捕获阶段**能收到，单独监听并在 230ms
  后（箭头动画结束）补一次测量；
- 原生侧 `heightListener` 里改 `layoutParams.height`；
- 首帧用「上次量到的高度」，没有就按字数估算 —— 避免"先塌成 0 再撑开"。

纵向滑动必须交还父列表：WebView 一旦判定滚动就会
`requestDisallowInterceptTouchEvent(true)`，父 RecyclerView 再也拦不到，
表现是"手指划在消息上整页不动"。`onTouchEvent` 里检测到纵向拖动就
`return false`，点击（展开折叠栏）不受影响。

### 18.6 安全

消息来自模型 → 不可信。WebView 必须开 JS（marked + 高度回传都要），
所以新增 `HtmlSanitizer`：

- 剥 `<script>` / `<iframe>` / `on*` 事件属性 / `javascript:` 链接；
- 外观设置里打开「允许美化脚本」才放行（给需要状态栏/按钮的卡）；
- 位图路径与列表 WebView 共用同一套规则（原来的 `CardRenderer.sanitize` 已合并进来）。

刻意不做 DOM 白名单：角色卡美化大量使用自定义标签，白名单会把正常内容一起删掉。

### 18.7 降级链

```
含标记 → WebView（真渲染）
  ├─ 用户关掉「富渲染」→ 纯文本（含 <details> 时用原生折叠块）
  ├─ 超过 20 万字符    → 纯文本
  ├─ 流式生成中        → 纯文本（生成完自动切回）
  └─ 3 秒没回传高度    → 纯文本（防白气泡：assets 缺失 / ROM 阉割 WebView）
```

### 18.8 验证

无模拟器（沙盒无 KVM），用宿主机无头 Chromium 直接跑 `assets/msg/render.html`：

- `window.DHP` 就位、`marked` 加载成功；

- 截图确认：折叠卡片有淡底 + 圆角 + 左竖条 + 三角（展开/收起两态都对）、
  表格有边框与表头底色、引用有左竖线、行内代码/加粗/删除线正常；
- DOM 量算：`table.clientWidth == #m.clientWidth`（无横向溢出）、

`:app:compileDebugKotlin --rerun-tasks` 全量通过；`_bridgecontractcheck` /

### 18.9 与 §17 的关系

§17 的 `FoldParser` / 原生折叠块**没有删**，降级成 fallback：用户关掉富渲染时，
含 `<details>` 的消息至少还能展开。`CardRenderer`（位图）同理保留但不再主动触发。

## 19. 整页 HTML 卡片：iframe 沙箱渲染 + 回收池落地（2026-11-08）

### 19.1 又一个「变成源码」的形态

§18 之后用户发来三张截图：**整条气泡里全是 HTML 源码**。

根因：美化预设输出的卡片通常长这样 —— ```html 围栏里包一份完整的
`<html><head><style><body>` 文档。§18 的链路里这份东西交给 marked 解析，
而 marked 只认 Markdown 和内联片段：整份文档会被当成 **fenced code block**
转义后塞进 `<pre>`，`<style>` 不生效、标签全部字面显示 —— 就是截图的样子。

浏览器的标准答案只有一个：**整页文档要当独立文档渲染，也就是 iframe**。

### 19.2 render.js 的「形态分流」（重写）

```
segmentsOf(raw)
  ├─ 先按 ``` 围栏切开（围栏外的剧情/选项不能丢）
  ├─ 围栏内是文档（<!DOCTYPE html / <html / <head）→ 抽出来
  ├─ 没有围栏且整条消息开头就是 <html> → 整条当文档
  └─ 其余 → 一次 marked.parse（绝大多数消息，和 §18 完全一致）
```

判定只依据 **web 标准标记**，不列标签白名单、不猜某个预设的写法。
关键收紧：只有「围栏内确实是文档」或「整条从开头就是文档」才走 iframe；
不能 `contains('<html')` —— 正文里聊到 `<html>` 的混合消息会被误判。

### 19.3 iframe 沙箱 + 高度探针

```js
f.setAttribute('sandbox', 'allow-scripts');   // 不给 same-origin / top-navigation / popups
f.srcdoc = full;
```

- 沙箱里的脚本在 **opaque origin** 运行：碰不到宿主的 `DHPBridge`、
  读不了 `file://`、跳不走整个气泡。给「允许美化脚本」的用户一个
  能跑状态栏/按钮的沙盒，而不是裸开权限。
- sandbox 不给 `allow-same-origin`，父页**读不到** `contentDocument`，
  所以高度只能由 iframe 自己 `postMessage({__dhpH: h})` 报上来；
  宿主按 `contentWindow` 匹配回传来源。
- 探针脚本由 render.js 注入到 srcdoc 末尾（load/延时/ResizeObserver 三重回报），
  预设作者自己的 `updateIframeHeight` 消息（`height` / `iframeHeight`）也兼容。
- 作者没写 viewport 时补一个；没写 body 背景时保持透明；`max-width:100%`
  兜底挡住大图撑破气泡 —— 作者自己的 CSS 仍然优先。

### 19.4 allowScript 与沙箱的关系（自洽）

`HtmlSanitizer.clean(rich, allowScript=false)` 在 **Kotlin 侧**剥掉
`<script>` / `on*` / `javascript:` —— 所以 iframe 沙箱恒给 `allow-scripts`
没有矛盾：`allowScript=false` 时根本没有作者脚本可跑，只有我们的探针；
`allowScript=true` 时作者脚本也只能在 opaque origin 里跑。

### 19.5 回收池真正落地

§18.4 表格里的「回收池上限 2」当时只是计划 —— 常量 `MAX_WEB_POOL` 定义了
但从未生效。本轮补上：

```kotlin
override fun onAttachedToRecyclerView(rv: RecyclerView) {
    super.onAttachedToRecyclerView(rv)
    rv.recycledViewPool.setMaxRecycledViews(TYPE_HTML, MAX_WEB_POOL)   // = 2
}
```

懒加载不用另做：`onBindViewHolder` 只在条目进入可见区（或 GapWorker 预取）
时调用，WebView 在那一刻才收到内容；`onViewRecycled` 里 `reset()` 清空，
旧内容不会闪到新消息上。

### 19.6 交付

- `app/src/main/assets/msg/render.js`：形态分流 + iframe srcdoc + postMessage 高度
- `app/src/main/java/.../chat/ChatAdapter.kt`：`onAttachedToRecyclerView` 池化上限
- 验证：无头 Chromium 确认 `hasIframe:true`、高度来自 postMessage、`<pre>` 消失；
  卡片截图渐变/圆角/徽章正常；APK 内 `assets/msg` 四件 + `HtmlMessageView` 均在包。

### 19.7 端到端验证揪出的误判（收尾修复）

五形态无头验证（md / details 片段 / ```html 围栏文档 / 裸文档 / 正文提及
`<html>`）第一轮发现：**无语言标注的代码围栏里提到 `<html>` 会被整块劫持
进 iframe** —— 正文讲解标签用法的常见写法被当成文档。

判定改为随语言标注分级收紧：

| 围栏写法 | 判定 |
| --- | --- |
| ` ```html `（作者明确标注） | 含文档标记即抽（`<!DOCTYPE html` / `<html` / `<head`） |
| 无标注 | 从开头是文档 **且** 含闭合标记（`</html>` / `</head>` / `</body>`） |

修复后五形态全部 PASS：代码示例保留为 `<pre>` 代码块，美化卡片照常走
iframe；`fence-doc` 样本确认围栏外的前后剧情不丢。

## 20. 气泡左右翻 / 卡片脚本被剥 / 重新发送 / 重新生成带预设（2026-11-09）

### 20.1 「能左右翻」：横向溢出没锁死

用户截图：整条 AI 回复能左右拖动，每行字被横向切掉半边，下面的正文还被
一块空白挤开。两个独立的成因：

| 成因 | 修复 |
| --- | --- |
| 预设卡片里写 `width:900px` / `white-space:nowrap`，WebView 内容比视口宽，水平拖动被当成内部滚动 | `render.css`：`html/body/#m` 加 `overflow-x:hidden!important`、`max-width:100%`；`#m *` 的 `max-width:100%` 提到 `!important`（才压得住作者内联 style）；长代码改 `pre-wrap` |
| iframe 内部同样会横滚 | `render.js` 往 srcdoc 的 head 与 body 末尾各注入一份 `!important` 宽度锁（作者后写的 `<style>` 也覆盖不了）；`HtmlMessageView.onTouchEvent` 只要检测到明显拖动就把事件交还父列表，WebView 不再自己滚任何方向 |

**下方空白**是另一个真 bug：高度探针用 `documentElement.scrollHeight`，它
至少等于 iframe 当前视口高度（首帧 160px），折叠后的卡片永远缩不回去，
把下面的正文挤开。改用 `document.body.scrollHeight/offsetHeight`（body 高度
由内容决定），首帧占位降到 96px，并加了 2.5 秒不上报时的长度估算兜底。

### 20.2 「正则没正常生效」：不是没跑，是脚本被剥了

对照用户导入的预设（Meowssiah 1.9.12）看，14 条内嵌正则里
「前端综合面板」会吐出一份 **32KB 的整页 HTML 卡片**（```html 围栏包
`<html><head><style><script>`），卡片里的行动选项全靠文档内脚本
`parseAndRender()` 动态生成，还自己 `postMessage({type:'resizeIframe',height})`。

旧版 `HtmlSanitizer.clean(allowScript=false)` 一刀切剥掉所有 `<script>`，
于是卡片只剩静态空壳、选项变成裸 emoji 文本 —— 看起来就像"正则没生效"。
截图里能看到的粉色标题条恰好证明正则**跑了**，只是内容被剥了。

修复：清洗前先把"会进 iframe srcdoc 的整页文档块"抠出来用占位符保护，
片段照旧剥 `<script>`/`<iframe>`/`on*`/`javascript:`，最后原样还原。
**文档块里的脚本一律保留** —— iframe 是 `sandbox=allow-scripts` 的
opaque origin，碰不到宿主 DHPBridge、读不了 file://、跳不走气泡；
ST/Tavo 的美化卡片本来就靠脚本，剥掉等于把渲染结果扔了。
判定与 `render.js` 的 `segmentsOf` 同一套（```html 标注 / 无标注需完整文档），

## 21. 底部可折叠摘要 / 选项没替换成功：SPreset 预设脚本运行时（2026-11-09）

### 21.1 现象与真正的根因

用户反馈：Meowssiah 1.9.12 预设里「前端综合面板」选项明明是开的，但底部
那个类似折叠床的可折叠摘要 / 行动选项**始终不出现**；以前在 Tavo 里用同一份
预设是能出来的。

前面 §18–§20 已经把 WebView 真渲染、iframe 沙箱、卡片脚本保护、高度回传
全都修好了，但这次的问题**不在渲染链路**。用真实 Kotlin 引擎逐条跑完 14 条
内嵌正则后确认：`[13] 前端综合面板` 本身完全正常，它匹配
`<options>` / `<summary>` / `<comment>` 标签块，替换串是 32KB 整页 HTML。
问题是**模型根本没吐出这些标签**——它连输入都没拿到。

Tavo / SPreset 这类预设的面板是「模型用工具调用返回结构化字段」生成的：

```
模型输出(tool_calls)
  └─ OutputPreprocessing.toolCallFormatter  →  <summary>…</summary> 等标签
      └─ 显示正则「前端综合面板」            →  整页 HTML 卡片
          └─ WebView / iframe                 →  美化折叠面板
```

而请求也不是把组装好的 messages 直接发出去：`FinalRequestProcessing` 会在
请求前扫描消息里的 `<<<|catgodml|…>>>` 指令、剥离宏、按 `registerPart`
动态拼出工具 schema，注入 `tools` / `tool_choice`，并把整段 messages 重写成
few-shot 结构。少了这一层，模型不会返回 `tool_calls`，显示正则就成了空转。
之前「正则开了却没生效」的所有排查都指向同一个结论：**缺的是生成链路的
工具调用协议，不是正则、清洗或渲染。**

### 21.2 为什么做「通用运行时」而不是再打一个针对性补丁

调研 `starowo/SPreset`（原作者 SoliUmbra 开源的 SillyTavern 扩展）后确认：
它是 111KB 的 ST 扩展，依赖 `SillyTavern.getContext()`、`eventSource`、
`promptManager`、jQuery 设置界面，**没法直接嵌进安卓原生工程**。但预设自带
的那几段脚本是**纯函数**，实测不引用 `SillyTavern` / `window` / `document` /
`tavo` / `ctx` 任何宿主 API —— 可以直接在现有 WebView 的 JS 引擎里
`new Function` 执行。

所以方案是做一个**不认识任何具体预设**的运行时：不写死 `soliumbra_reply`、
`registerPart`、`summary` / `options` 这些名字，只通用地执行预设自带脚本。
换一份同样带 `extensions.SPreset` 的预设，只要脚本接口一致就能用；这正是
用户担心的「换个预设又不好使」的答案。

顺带说明：这里只需要**单轮结构化输出**——请求带一个工具定义 → 模型返回
一次 `tool_calls` → 跑一次脚本把字段转成标签 → 交给已有 `[13]` 正则渲染。
不需要多轮工具执行，也不需要外部工具调用，更不是智能体循环。

### 21.4 三个容易踩的坑（都在实现里处理了）

1. **只跑 `FinalRequestProcessing` 不够**。它单独跑只会注入 `context` 工具；
   真正的 `soliumbra_reply` 定义在 `SPreset.ToolBindings` 里（一段
   `return {name, description, parameters, action}` 代码）。必须先执行绑定生成
   `tools` 放进 request，脚本才会按 `registerPart` 给它动态补字段。
2. **脚本末尾带不带分号都有**。Meowssiah 的 `FinalRequestProcessing` 末尾是
   `}`（纯表达式），`toolCallFormatter` 末尾却是 `};`（表达式语句）。一律
   用 `return (…)` 包裹会让后者变成 `return (…;)` 直接语法错 —— 编译改为
   先试「直接 return」，失败再退回括号包裹。
3. **`registerPart` 指令不是集中在一处**，而是散落在 5 个**已启用**的 prompt

### 24.2 `soliumbra_reply` 到底是什么

不是查天气、读文件那种外部工具，是**结构化输出模板（伪工具）**。
`prompts[9]「召唤术」` 原文：「本喵给他们的聊天偷偷加个 `soliumbra_reply` 工具，
然后在 content 里面先用 `<think_nya>` 好好想想怎么回复」；`prompts[30]` 里的
`<run_tool_replacement>` 是触发开关。

它的价值是**保证标签齐全**：schema 把回复拆成 `think_nya` / `game_content` /
`summary` / `comment` / `options` 固定字段，`tool_choice=required` 逼模型逐项填，
响应后 `toolCallFormatter` 再把字段包回标签 → `[13]` 一定有输入。纯文本路径
靠自然语言约束，Gemini 3 这次就没遵守，直接吐散文。

顺带澄清「只有傻酒馆能用？」——这套机制要三件事，别混为一谈：

| 层 | 干什么 | 谁提供 | 只有 ST 能用？ |
| --- | --- | --- | --- |
| ① 请求带 `tools` / `tool_choice` | 发工具定义 | OpenAI 兼容协议 | 否，支持 function calling 的中转都行 |
| ② 剥私有宏、重写请求、`tool_calls` → 标签 | 调度 | `SPreset` 扩展（`inject.js` 111KB） | 是，绑死 `SillyTavern.getContext()` / `eventSource` / `promptManager` / jQuery |
| ③ 把 32KB 整页 HTML（含 `<script>`）渲染成卡片 | 显示 | 客户端渲染器（iframe `srcdoc` + 允许脚本的沙箱） | 否，谁实现谁能显示 |

`starowo/SPreset` 的 `inject.js` 里确实有 `document.createElement('iframe');
iframe.srcdoc = htmlText; sandbox.add('allow-same-origin')…` —— 渲染整页 HTML
本来就是宿主扩展的活，不在预设 JSON 里。Tavo 自己重写了 ②③，新版没接住 ③。

### 24.3 为什么第一版翻车、这一版怎么绕开

第一版执行 `FinalRequestProcessing` 把 **35 条 system 重写成 8 条 few-shot**，
角色设定只剩 `context` 工具描述，再叠 `tool_choice=required` → 模型按 Gemini
默认身份拒答。

关键发现：`ToolBindings[*].code` 是静态 `return {...}`，schema **只有
`think_nya` 一个字段**；`game_content` / `options` / `summary` / `comment` 是
`FinalRequestProcessing` 扫描 messages 里 `<<<|catgodml|registerPart:…>>>` 后
**动态补进去的**。所以「只注入 ToolBindings、不跑脚本」拿不到完整 schema。

温和版做法（`generateService.ts`）：

1. 用**含宏**的 `finalMessages` 跑 `applyRequest`，让脚本算出完整工具定义；
2. **丢弃**脚本改写的 8 条 few-shot，只取 `patch.tools`；
3. 发送仍用 `stripPrivateDirectives` 清洗后的 **36 条消息**（35 system + 1 user），
   私有宏清零、标签指令全保留；
4. `tool_choice: 'auto'` 而非 `required`；**不传 `rawMessages`**，
   `apiClient` 默认就用传入的 messages；
5. 响应若有 `tool_calls` → 已有 `formatToolCalls` 包成标签；没有 → 原文原样。

因此这是**只赚不亏**的一层：模型用工具 → 标签齐全、`[13]` 必命中；模型不用 →
完全退回纯文本路径，零回归。无 `SPreset` 的预设整段跳过，请求逐字节不变。

## 25. 渲染插件位（内置插件库 · 随时安装/卸载 · 不可删除）

### 25.1 为什么做这个，而不是做那个功能

Discord 社区实测把结论钉死了：底部折叠面板**不是傻酒馆本体渲染的**，
而是第三方插件层做的 —— 酒馆助手（`N0VI028/JS-Slash-Runner` 4.12.0）、
小白X（`RT15548/LittleWhiteBox` 3.2.5）。两者都扫 `.mes_text pre` 各自挂
iframe，再叠加小白X 往 `body` 加 `xiaobaix-active` + `pre{display:none}`
的全局 CSS，于是「渲染两次 / 闪烁 / 消失」；酒馆助手官方 FAQ 直接写着
「关闭小白X 等拥有前端渲染功能的插件」。加上全局/局部/预设正则按顺序执行，
世界书多一条状态栏条目就会把 `<options>` 吃掉 —— 这就是「没选项」。

**用户拍板：功能不做，位置先留。** 理由是预设生态会变：这回是 ` ```html `
整页，下回可能换语言标注、换片段写法、换自造容器标签。与其每次往主 App
打补丁，不如把「预设怎么写」外置成插件，以后换写法就卸载旧的、内置个新的。

### 25.2 语义（关键约束）

- 插件**随 APK 打包在内置插件库** `PluginCatalog.ALL`，目前没有云端库、
  也没有发布页，所以先内置。
- 设置页只提供「**安装 / 卸载**」运行时挂载 + 「启用 / 禁用」。
  **没有删除操作**：卸载只是把 id 从 `PluginStore.installed` 移走，
  插件本体仍在库里，随时能再点「安装」挂回来。
- `PluginStore` 只持久化 `installed` / `enabled` 两个集合，独立 SharedPreferences
  `dhp_render_plugins`，不动 `Appearance`、不动会话、不动网页 IndexedDB。

### 25.3 架构：旁挂，不重构

链路没变，只在决策点前置加了一个槽：

```
模型输出 → transformForDisplayRich → decideRender()
                                       ├─ PluginRegistry.resolveHtml()
                                       │    ├─ 无插件/全 Pass → null
                                       │    └─ 认领 → 一串 HTML
                                       └─ HtmlSanitizer.clean(插件结果 ?: rich)
                                            → web(WebView/iframe) | fold | plain
```

- **零插件时 `decideRender` 的原有三行逐字节不变**（`pluginHtml` 为 null，
  `effective = rich`）——这是零回归的保证。
- 插件输出**不写回** `RenderedMsg.rich`：缓存里永远存原始 rich，
  因为 `renderCached` 命中分支会重跑 `decideRender`；若把改写结果写回缓存，
  下次命中就会二次改写。给界面的内容走 `web` 字段。
- 插件只能返回一串 HTML，后面 WebView / iframe / `render.js` 的
  `segmentsOf` 整套完全复用，**主渲染管线一行都没重写**。

新增文件（`chat/render/plugin/`）：`RenderPlugin.kt`（契约）、
`PluginStore.kt`（状态）、`PluginCatalog.kt`（内置库 + 围栏适配 + 两个插件）、
`PluginRegistry.kt`（仲裁）、`settings/PluginSettingsActivity.kt`（设置页）。

修改（6 处，都是加行）：
`ChatController.kt`（decideRender 加 `meta` 参数与前置 hook；
renderCached/renderAi 透传 `PluginRenderMeta`）、
`SettingsHomeActivity.kt` + 布局（设置首页入口）、
`RenderSettingsActivity.kt` + 布局（渲染设置页入口）、
`AndroidManifest.xml`（注册 Activity）。

### 25.4 内置的两个插件（写法适配器，不是功能）

| id | 名称 | 优先级 | 认领的写法 |
| --- | --- | --- | --- |
| `frontend_card_strict` | 前端卡 · 严格整页 | 100 | 围栏里是完整 HTML 文档；把非 `html` 的语言标注统一改成 `html`，救回「文档前带生成注释 / BOM」这类 `DOC_START` 失败的写法（对齐酒馆助手保守约定） |
| `frontend_card_loose` | 前端卡 · 宽松片段 | 90 | 任意围栏里的 HTML 片段（`<div>/<style>/<details>…`）或含 `<script>`；补成独立文档 + 标 `html`（对齐小白X 宽松约定） |

两者**只改围栏标注、必要时补文档骨架**，不实现折叠面板、不碰正文、
不碰正则、不碰请求。已是标准 ` ```html ` 时插件放行（Pass），交回内置处理。

`FenceAdapter.rebuild` 有个实测踩过的坑：补完文档后必须保证闭合 ` ``` `
独占一行，否则 `render.js` 的 `FENCE`（`^[ \t]*```[ \t]*$`）匹配不上，
整段会被当 Markdown 显示成源码。

### 25.5 六条不变量

1. **一条消息最多一个 renderer**：按 `priority` 降序取第一个认领者，
   多个认领只记警告；结构上免疫社区「两个渲染都开了」。
2. 没装插件 / 全 Pass / `apiVersion` 不匹配 / `scope` 不匹配 → 回退内置。
3. `PluginScope.Presets(ids)` 让插件按预设绑定，换预设自动失效。
4. `PLUGIN_API_VERSION` 契约校验：App 升级后不兼容的插件跳过并提示，不崩。
5. 激活返回 `Disposable`，卸载 = dispose + 移出注册表 + 丢内存缓存，零残留。
6. 插件输出仍过 `HtmlSanitizer.clean`，`iframe sandbox="allow-scripts"`
   且不给 `allow-same-origin` 的安全边界不变。

### 25.7 以后预设换写法怎么办

在 `PluginCatalog.ALL` 里加一条 `RenderPlugin`：

1. 写 `PluginDescriptor`（id / 名称 / 约定 / 版本 / priority / scope）；
2. 实现 `claim()`（认领哪种写法）与 `render()`（规范化成内置认得的
   ` ```html ` 整页，**必须幂等**）；
3. 把实例加进 `ALL`，设置页自动出现，可装可卸。

主 App 其余部分不用改。旧插件不用了就在设置页卸载，它仍留在库里。

## 26. 插件位升级为「通用前端卡渲染器」（2026-11-09 03:58）

### 26.1 勘误：上一版把目的丢了

§25 的 P0 把内置插件实现成「只改 ` ``` ` 围栏语言标注的**写法适配器**」，
并在说明里写了"不实现折叠面板、不生成选项"。用户明确指出这是误解：

> 「我之前说不想做的意思是不想再去搞插件，但是又不得不搞。**折叠窗什么的
> 还是要的，我们就是为了适配而做的**」
> 「这个插件的功能我们本来就是**抄的人家渲染的功能**，是一个简单的通用兼容
> 功能，做！我很确定要做，**只是不干扰我们主 app 的运行**」

即：插件位（可装可卸、内置库、主 App 不动）方向正确，但插件**本身必须真的
能渲染**。不做"针对具体预设打补丁"这条约束，恰恰因为补丁被**隔离进可卸载
插件**而消解——换写法就卸载旧插件、内置个新的顶上。

### 26.2 改法（只动插件库，主链路零改动）

`PluginCatalog.kt` 重写，两个内置插件从"改语言标注"升级为**通用前端卡渲染器**：

| 对齐 | 抄的机制 | 落地 |
| --- | --- | --- |
| 判定 | 酒馆助手 `is_frontend` / 小白X `shouldRenderCodeBlock` | `isFullDoc` / `isFragment`：认 HTML 整页 / 片段，**不认任何预设专有标签** |
| 渲染 | 酒馆助手 `createSrcContent` | `hardenDoc()` 只往 `<head>` 注入 viewport / reset CSS / `--TH-viewport-height` / 横滚锁 / 加固标记；`toDocument()` 把片段补成独立文档 |
| 挂载 | `Wrapperiframe` / `createSrcContent` | `rebuild()` 统一标 ` ```html `、闭合围栏独占一行，交给现有 iframe `srcdoc` + `sandbox="allow-scripts"` |

**最关键的一条**：`hardenDoc()` **只动 head、绝不碰 body**。预设模板的
`<template id="raw-data">$1</template>`（`<summary>/<comment>/<options>` 标签
数据）与生成折叠窗的 `<script>` 全在 body，必须逐字节保留——折叠窗正是靠
它们跑出来的。这也是上一版"缺标签"根因的正确落点：**插件不造 UI、不补标签、
不改模型输出，只保证预设吐出的卡片能被完整渲染成界面**。

幂等：加固后 head 带 `dhp-render-plugin` 标记，二次运行 `claim`/`render`
直接放行。仍是「一条消息最多一个 renderer」仲裁。零插件时 `resolveHtml()`
立即返回 null → `effective = rich` → `decideRender` 原有三行逐字节执行。

## 27. 实测诊断：折叠窗只有一条横线 —— 补「面板数据适配器」（2026-11-09 04:19）

### 27.1 用户实测反馈

装了 0358 版、启用「前端卡渲染器 · 严格整页」、重新生成剧情、显示正则调了几次，

### 27.2 根因：断点在正则之前，不在渲染层

| 环节 | 事实 | 后果 |

## 29. 真根因：插件吃错了输入形态（`<br>` rich）+ APK 内自检（2026-11-09 04:5x）

### 29.1 反馈与四个方向

### 29.2 真根因（与气泡 / WebView / iframe 无关）

`ImageMarker.transformForDisplayRich`（`stcore/.../ImageMarker.kt:272`）交给插件的 `rich.html` 有**两种形态**：

| 形态 | 触发条件 | rich 长什么样 |
| --- | --- | --- |
| A 原样文本 | `isFullHtmlDocument(stripped)` 命中（消息里含 `<!DOCTYPE html` / `<html` / `<head`） | 保留 `\n`，`---` 独占一行 |
| B HTML 化 | 普通消息走 `htmlifyNewlines` | **每个 `\n` 变成 `<br>`，整条消息是一整行**；`---` 被 `<br>` 夹住不再独占行 |

旧插件（§27、§28）按 `\n` 分行、要求 `---` 独占一行、`isOptionStart` 看行首 —— 只在形态 A 下成立。**用户这条消息没有折叠栏卡片时走形态 B，于是 `claim` 恒为 false，整条放行，界面只剩正文和 marked 把 `---` 渲染出的 `<hr>`**。用户「复制出来的输出里看不到 `----`，截图里却有一条横线」也正好对上：`<hr>` 是渲染元素，不产生可复制的字符。

**为什么沙盒一路全绿、APK 里没出来**：单测喂的是原始 Markdown（`\n` 分行），端到端验证也是我自己复刻 `splitSegments` + 自建宿主页，绕过了 `transformForDisplayRich` 的输出形态、也绕过了真 `HtmlSanitizer` 和 `render.html`。三处都不是真机输入，所以验证结论不成立。

### 29.3 修法：等长归一化（只动 `PanelDataAdapter`）

- `scanView(rich)`：把 `<br>` / 块级闭合标签换成 `\n` + **等长空格**，`<hr>` 换成 `\n---` + 等长空格。字符偏移与原始 rich 完全一致，于是「扫描用的行坐标」可以直接切原始字符串。
- `head` 取**原始 rich**（保留主 App 的 `<br>` 排版，正文一点不乱），`tail` 取归一化视图（可按行拆散文）。`headEnd` 落在分隔线前一个行边界，既不把 `<br>` 劈成半个 `<`，也不把 `---` 留成孤立横线。

## 30. 第三轮实测：诊断终于说清了问题 —— 定位不再依赖围栏（2026-11-09 05:1x）

### 30.1 诊断给出的三条硬事实

用户装 `0450` 后贴出的「渲染自检」：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 输入形态 | 原样换行文本 · 12057 字符 | **不是** `<br>` 形态，上一轮修的那条不是本次断点 |
| `rich 开头` | ` ```↵<!DOCTYPE html>↵<html lang="zh-CN">↵<head>↵  <meta charset="UTF-8" />…` | 放大截图后 `↵` 清晰可见：折叠栏卡片与正文**都带换行**，rich 没有被压平 |
| 插件认领 | `panel_data_adapter=否`，生效插件「无（全部放行）」 | 认领这一步就断了，根本没进渲染 |

自检渲染（用 APK 内置模板走 `HtmlMessageView`）在气泡里完整出图 ⇒ 模板、气泡、iframe 全都没问题，**唯一断点仍是 `claim`**。

### 30.2 真因：围栏配对按「行」数，一处没闭合就把整条正文吞掉

旧实现 `fenceRanges()` 是「行首是 ` ``` ` 就当一个围栏标记」，两两配对，**没闭合的那一段一直延伸到字符串末尾**。而 rich 里围栏的形态并不稳定：

- 闭合围栏可能黏在 `</html>` 后面（同一行）；
- 卡片可能被预设/上游压成一行（一行里出现两个 ` ``` `，按行数只数到一个）；
- 模型偶尔自己写一个 ` ``` `，标记数变成奇数。

以上任一情况，配对都会错位，`inFence()` 把**卡片之后的全部正文**判成「围栏内」→ 选项行一个也扫不到 → `claim=false`。这解释了「插件设置页显示已启用、气泡里却什么都没有」以及「沙盒里怎么测都是绿的」：沙盒 fixture 的围栏永远是规规矩矩独占一行。

### 30.3 改法（仍只动 `PanelDataAdapter` 内部）

1. **正文定位改成「最后一个 `</html>` 之后」**（`splitTail`）。整页卡片的结尾是确定的，与围栏怎么写完全无关；卡片后面的闭合 ` ``` ` 顺带划进卡片区，正文里不留孤立围栏。没有整页文档时才退化为「最后一对围栏之后」。

## 32. 正文被吃进面板的根因：`promptOnly` 判断写反 + 散文兜底该删（2026-11-09 05:4x）

> **勘误（2026-11-09）**：§32.1 对 SillyTavern 判定的描述有误。ST 源码（`getRegexedString`）是「或」关系 —— 双 true 的脚本在显示和提示词两侧都会执行，并非「显示侧跳过 promptOnly」。正确的取舍与理由见 **§33.1**。正文保留原样，方便对照当时的判断过程；以 §33 为准。

用户实测：「把正文也给搞进去了」，并指出正确方向 —— **人家的功能是开放式的，是预设去用这个功能，不是我们去搞这个预设，包括折叠选项。**

### 32.1 两个真因

**① `[12] 行动选项2` 在显示侧被执行，把 `<options>` 整段删了**

预设里 `[12]` 是 `markdownOnly=true` + `promptOnly=true`。SillyTavern 的判定是：

```js
if (script.promptOnly && isMarkdown) return;   // 显示侧：跳过 promptOnly
if (script.markdownOnly && !isMarkdown) return; // prompt 侧：跳过 markdownOnly
```

我们的写法是 `if (promptOnly && !markdownOnly) continue` —— 两个标志都为 true 时**不跳过**，于是显示时把 `<options>` 删掉。

探针（App 自己的引擎跑真实结构）：

| 修前 | 修后 |
| --- | --- |
| `[12] matches=1`（删掉 options） | `[12]` 被跳过 |
| `[13] matches=1`，卡片里**选项=0** | `[13] matches=1`，卡片里**选项=3** |

也就是说：**`[13] 前端综合面板` 一直是能出卡片的**，只是选项被前一条正则吃掉了，看起来像「预设没生效」，才逼出我那一层散文兜底。

**② 散文兜底用 `---` 定位，把正文末尾吃进悄悄话**

模型没吐标签时（这次它写成了散文），`PanelDataAdapter` 取「最后一条 `---` 之后」当面板区。预设要求「用 `---` 分隔段落」，最后一条分隔线常常落在正文中间，于是正文后半段全被当成面板内容，塞进了「小猫之神的悄悄话」。

### 32.2 改法：把「预设的事」还给预设

1. **`RegexEngine` 对齐 ST**：显示侧 `if (promptOnly) continue`；构建 prompt 时 `if (markdownOnly) continue`。`[12]` 不再误删选项。
2. **删掉散文 → 模板的适配**（整段删除，约 400 行）：不解析 `<summary>` / `<options>` / `<comment>`，不猜散文，不生成面板。
3. **插件退回纯渲染器**：`FrontendCardPlugin`（id 仍 `panel_data_adapter`，3.0.0，名称「通用前端卡渲染器」）只做三件事 —— 完整网页补 head（viewport / reset / vh / 横滚锁）、片段包成独立文档、非 html 围栏标注统一成 ` ```html `。面板长什么样、有没有折叠，由预设自己的正则与模板决定。
4. **自检不再依赖预设模板**：改成一张自带脚本的内联卡片（点按钮变绿），验证「WebView / iframe / 脚本 / 高度」四件事；`assets/plugins/meowssiah_panel.html` 从 APK 移除（少 32KB）。

## 33. 选项按钮真正可用 + 宏补齐 + 一张「还差什么」的核查表（2026-11-09 05:5x）

### 33.1 先更正 §32 的一处说法（重要，别照着 ST 改回去）

§32 写的「SillyTavern 的判定」是错的。ST 的 `getRegexedString` 实际是**或**关系：

```js
if ((script.markdownOnly && isMarkdown) ||
    (script.promptOnly && isPrompt) ||
    (!script.markdownOnly && !script.promptOnly && !isMarkdown && !isPrompt)) {
    // 执行
}
```

也就是说：**ST 里「双 true」的脚本，显示侧和提示词侧都会跑**。Meowssiah 的 `[12] 行动选项2`（双 true、替换成空串）在 ST 里会先删掉 `<options>`，后面的 `[13]` 就再也拿不到选项 —— 这很可能就是 Discord 里那句「没选项」的来源。Tavo 的引擎在显示侧跳过 `promptOnly`，所以同一个预设在那边正常。

我们因此**不照抄 ST**，而是分开处理：

| 场景 | 判定 | 理由 |
| --- | --- | --- |
| 显示 | `promptOnly` 一律跳过 | 保住 `<options>` 交给 `[13]` 出卡片（与 Tavo 实测一致） |
| 提示词 | 只跳过 `markdownOnly && !promptOnly` | 双 true 照常执行 —— 作者写 `promptOnly` 就是想让它进模型前消失 |
| 双 false | 两边都跑 | ST 是把改写结果存进聊天记录；我们存原文、每次重算，必须补这一步才等价 |

单测 `双 true 脚本 显示跳过 提示词执行`、`纯显示脚本不进提示词` 锁住这三条。

### 33.2 卡片选项点了没反应 —— 补「宿主兼容层」

预设卡片不是自己发请求，而是照 SillyTavern 的写法操作宿主：

```js
const ta = window.parent.document.getElementById('send_textarea');
ta.value = '选项文字'; ta.dispatchEvent(new Event('input'));
window.SillyTavern.getContext().generate();
```

原生 App 里 `parent.document` 根本不存在（iframe 是 opaque origin），第一步就被 `try/catch` 吞掉，表现就是「选项画出来了，点了没反应」。

改法（**不针对任何预设，只补 ST 的契约**）：

1. `render.html` 放两个真实元素 `#send_textarea`（readonly，不弹键盘）、`#send_but`，挪到可视区外而不是 `display:none`（后者会让 `focus()/setSelectionRange` 失效）。
2. `render.js` 新增 `HOST_SHIM`：搭出 `window.SillyTavern`（`getContext` / `generate` / `sendMessage` / `saveSettingsDebounced` / `eventSource`），注入 iframe 的 `<head>`（早于卡片脚本）与父壳各一份。
3. `sandbox` 从 `allow-scripts` 改为 `allow-scripts allow-same-origin` —— 不给同源，`parent.document` 依然抛 SecurityError。代价是卡片能摸到本壳 DOM 与 `DHPBridge`；桥只暴露 `height / input / send / getSettings / saveSettings` 五个无权限接口，且 `allowFileAccessFromFileURLs=false`，风险限制在一条气泡内。
4. `HtmlMessageView.Bridge` 增 `input / send / getSettings / saveSettings`（都带长度上限），`HostListener` 转给 `ChatAdapter.Listener` → `NativeChatActivity`：
   - `input` → 写进原生输入框（「填入 / 追加」模式看得见）
   - `send` → 生成中先挡住（不然 `submitInput` 会先清空输入框，选项丢了），空闲时直接发
5. 卡片的「直接发送 / 仅填入 / 追加」开关走 `getContext().extensionSettings` + `saveSettingsDebounced`，落到 `SharedPreferences("dhp_host")`，跨气泡保持。

用户决定「除了预设都搞」，并强调两点：① 之后做群聊要复用这套机制；② 不能影响渲染插件。

### 34.1 为什么能不影响组装

组装链路（`bridge/generateService.ts: buildMessages`）在**请求时**从 assets store 读三样东西：
`getCurrentWorldBooks()` / `getCurrentRegexScripts()` / `getCurrentCharacter()`。
只要 store 里的数据与改造前逐字节一致，组装结果就一模一样。

所以方案刻意**不把归一化搬到原生**：ST 世界书的 entries 对象→数组、key 对象重建、字段补齐全在
`engine/stImport.ts`（被真实预设验证过），原生只做存储。引擎里的 store 仍是工作副本，
原生多了一层权威文件而已。

### 34.2 数据流

```
原生 filesDir/data/assets/assets.json     ← 唯一权威（原子写：tmp + rename）

        ▼
引擎 assets store（worldBooks / regexGroups / current*Ids）
        │ assets.save() → nativeManaged? → onAssetsChanged(快照)
        ▼
原生 assets.json
```

- 首次升级：原生为空 → 引擎把现有数据交出去（`handOverToNative`），然后把 app-data.json 里的
  `worldBooks / regexGroups / current*` 写成空数组并 flush —— **旧副本被缩掉，不留两份**。
- 接管后 `assets.save()` 只写 `characters / presets / currentCharacterId / currentPresetId`，
  世界书与正则不再进 app-data.json。
- 删除/导入/改名/开关仍走原来那批资产页命令（`assetRemove` / `wbSaveEntry` / `regexSaveScript` …），
  只是 save 之后多一步回传，UI 与命令层零改动。

## 38. 群聊容器 + 用户角色 + 修「换个角色再回来就串卡」

分支：`feat/group-chat`。这一轮动的是数据层，UI 只做最小可用。

### 38.1 群聊不是「一条时间线多个 AI」

结构定成 **一个群 + N+1 个普通会话**：

- 公共区 1 个会话（`GroupRef.kind = public`），用 `SessionAction.speakerId` 标发言人；
- 每个成员 1 个私聊会话（`kind = member`），完全复用单人聊天的分支 / 变体 / 摘要。

这样私聊频道不需要任何新消息模型，切频道 = 打开另一个 `sessionId`，上下文天然隔离；
只有公共区才需要多发言人标记。摘要也天然分开：成员摘要是个人经历，公共摘要是全场，
因为它们在各自的会话文件里（`nativeSummaries`）。

数据落点：

| 数据 | 位置 |
| --- | --- |
| 群标题 / 成员顺序 / 公共书 / 群预设 / 群正则 | `filesDir/groups.json`（`GroupStore`） |
| 频道归属 | 会话 JSON 的 `nativeGroup`（`groupId / kind / memberId`） |
| 成员私有书 / 成员预设 / 角色卡 | `session_bindings.json`（`SessionBindingStore`） |

群聊频道不进「冒险」列表：索引 `index.json` 里带了 `groupId / channelKind`，
首页在列表层就能过滤，不必把每个会话读一遍。

### 38.2 世界书分层 = 按「谁在说」取并集

| 频道 | 注入 |
| --- | --- |
| 公共区 | 群公共书 |
| 成员频道 | 群公共书 ∪ 该成员私有书（公共强制生效，成员去不掉） |
| 单人会话 | 完全按绑定（null = 跟随全局） |

成员的 `Binding.worldBookIds` 只存私有书，公共书在生成时从 `GroupStore` 现取 ——
换公共书立刻对全部频道生效，不用回写 N 个会话。

### 38.3 用户角色（persona）

资产页「角色」tab 拆成两块：角色卡库（AI 演谁）+ **我的角色**（你是谁）。

- 存 `filesDir/personas/`：`personas.json` + `avatar_<id>.jpg`（统一压到 512 长边）；
- 只影响两件事：`{{user}}` 的名字、`{{persona}}` / 用户人设块；
- 没有用户卡时行为与以前完全一致（回退预设的 `name_user` / 角色卡的 `persona`）；
- 人设块只在预设没引用时补一条 system，位置在角色卡之前（ST 的默认顺序）。

### 38.4 修串卡：会话自己记角色

根因：角色只在角色详情页「用它开聊」时写进网页全局 `currentCharacterId`，
会话文件不记。先跟 A 聊、再跟 B 新建、回 A 继续发，用的就是 B 的卡。

修法分三层：

1. `Binding.characterId / characterName`：空会话首次打开时，把引擎当前角色**固化**下来
   （只对空会话做，老会话继续跟随全局，不会被"现在选中的卡"污染）；
2. `window.__dhpGen.bindSession(sessionId, characterId)`：会话级映射，显示宏 `{{char}}`
   按会话取卡，不碰全局单例；
3. `GenBridge.request(characterId)`：每次生成再显式带一份，网页侧优先级
   「请求 > 会话绑定 > 全局」。

公共区用户自己发言时带 `noCharacter: true`：既没有成员在扮演，也不该把上次选中的卡
塞进去。

### 38.5 群聊页

- 顶部频道栏：公共固定第一个，成员按发言顺序；点谁切到谁的会话；
- **每个频道一个 `ChatController`**：切走后台继续生成。代价是每频道一个渲染线程，
  频道第一次点开才创建；
- 公共区输入栏多一个「续写」：按成员顺序轮转叫人；（**后来被 §40 收进「＋」菜单**）
- 公共区气泡显示发言人名字与头像（`speakerId → GroupStore 成员名 → 原生角色卡头像`）；
- 群设置：公共世界书（多选）、群预设（单选）、邀请成员、重命名、删除群聊。

## 39. 群聊补全：成员级 API、频道栏、搜索与摘要

分支：`feat/group-chat`。这一轮把 §38 列的"缺口表"逐项补掉，方向不变。

### 39.1 配置分三层，成员只存"显式改过的"

```
群（公共书 / 预设 / 运营商 / 正则） → 成员（私有书 / 预设 / 运营商） → 全局
```

- `Group.apiConfigId`：群级默认运营商；成员没单独选就用它；
- `SessionBindingStore.Binding.apiConfigId`：成员/单人会话单独指定的运营商；
- 生成时 `binding.apiConfigId ?? group.apiConfigId ?? 全局当前`，摘要走同一套
  （`SummaryService.run(apiConfigId)`），否则会出现"用 A 的接口聊、用 B 的接口摘要"。

数据上 null 一律表示"跟随上层"，所以换群 API 会立刻影响所有没单独选过的成员，
不需要回写 N 个绑定。`ConnectionStore.llmRuntime(uid)` 按 uid 现取；
uid 已被删除时回落到当前选中，界面那边显示成「已删除 · 跟随上层」——
删接口不该让聊天直接挂掉。

### 39.2 频道栏：换肤 + 顺序 + 成员入口

- **颜色全部走 `ThemeTokens`**（`ProviderUi`）。上一版是硬编码 `#2F66D8`，
  换一次皮肤频道栏就露馅；现在和运营商页是同一套取色规则；
- 未选中的成员收成「头像 + 顺序徽章」，选中才展开名字。三个成员就能把
  300dp 撑满，不收起后面的要靠盲滑；
- 头像用 `CharacterAvatar.bitmap(name)`（角色卡图）；没有图时退到
  `CharacterAvatar.letter()` 首字母圆，颜色跟主题走 —— 比统一灰占位好认人；
- **长按频道头像**：成员设置 / 设为下一位发言 / 移出群聊；
- **发言顺序**放在 ⋯ → 「发言顺序」面板里，↑↓ 即时写盘、频道栏立刻重排。

> 没有做"长按拖动排序"：频道栏在横向 ScrollView 里，拖拽和滚动手势会互相抢，
> 手指一抖就变成滚动。面板式排序在任何成员数量下都稳，且能一次看清完整顺序。

### 39.3 成员设置

每个成员一个面板：角色卡显示名、私有世界书、预设、运营商、移出群聊。

- 显示名与历史：消息只存 `speakerId`（角色 uid），改名后历史跟着变，不改旧消息；
- 预设/运营商都有「跟随群」选项，选了就是 `null`，不是复制一份群配置；
- 面板里的值就地更新（不关面板重开），保存前重新读一次绑定，避免连改两项时拿旧快照覆盖。

**移出成员**：从群成员里去掉，频道会话**不删**，而是清掉 `nativeGroup` 并改名
「（已退出群聊）」——它会回到「冒险」列表，历史还在。整群删除才连会话一起删。

### 39.4 群设置补全

⋯ 菜单现在有：公共世界书、群预设、群运营商、群正则组、发言顺序、邀请成员、重命名、删除群聊。

- 群正则组：多选，「恢复跟随全局」一键回到 null（字段与生成链路 §38 已通，这里补 UI）；
- 群运营商：说明写清楚"成员默认用它，个人界面可以单独改"。

### 39.5 搜索与摘要

- 顶栏搜索：只搜**当前频道**。同一个词再点一次 = 跳到下一条命中；
  切频道自动清空命中表（跨频道搜索的落点还没想好，不做半成品）；
- 顶栏摘要：调 `ChatController.summarizeNow()`，压缩的是**当前频道自己的会话**。
  成员频道缩的是个人经历，公共区缩的是全场，本来就在不同文件里，天然分开；
- 摘要进行中按钮变淡，完成后就地刷新。

### 39.6 兼容与兜底

  补一次。只补名字、不动 id —— 不会把"现在选中的卡"套到旧会话上；

## 40. 群聊的「＋」：续写 / 旁白 / 配图，旁白是群设置而不是角色卡（2026-11-11 23:3x）

### 40.1 为什么把「续写」收进加号

上一版「续写」常驻在输入框左边。公共区还行，切到成员频道就变成一块白占位置的按钮
（私聊只有一个角色，没有"轮到谁"的问题）；更要紧的是生图和旁白根本没有入口。

现在输入栏最左边是一个「＋」，点开在**输入栏上方**弹一小块菜单：

| 项 | 公共区 | 成员频道 |
| --- | --- | --- |
| 续写 | 按顺序叫下一位 | 让这个频道的主人接着说 |
| 指定谁说 | 跳过轮转直接点人 | —（不显示） |
| 旁白 | 发到公共区 | 先切回公共区再发 |
| 配图 | 给当前频道最新一条回复出图 | 同左 |

位置用 `Dialog` 的 window y 偏移算（输入栏高度 + 6dp），不用 `PopupWindow`：
后者在键盘弹起、刘海屏、导航栏三种情况下表现不一致，也拿不到主题底板。
动画复用已有的 `SheetAnim`（底部滑入），所以看起来是"从加号往上弹出来"。

### 40.2 旁白：一份群设置，不是一张角色卡

- 数据：`Group.narratorPrompt`（`groups.json`），空 = `GroupStore.DEFAULT_NARRATOR`；
  群设置 →「旁白设定」可改，带「恢复默认」。
- 身份：生成的 Action 用 `speakerId = GroupRef.SPEAKER_NARRATOR`（保留字 `narrator`），
  和成员发言共用同一条时间线、同一套变体 / 重新生成 / 摘要语义。
- 注入：请求带 `narratorPrompt`，web 侧 `injectNarratorIfAny` 补一条 system
  （排在用户角色之后、正则之前），**不注入任何角色卡**（`noCharacter = true`）。
- 导出：`SessionHistory.export` 遇到旁白的 speakerId 固定标 `【旁白】`，
  不依赖调用方传名字映射 —— 少一个映射就退化成"无主台词"，模型会当成自己说过的。
- 为什么不给旁白建角色卡：角色卡会进频道栏、参与「续写」轮转、被当成某个人物注入描述。
  旁白要的是**视角**，不是**人设**。

### 40.3 生图：抽成 `chat/QuickImage`

原来这套逻辑（读配置 → 取上文 → LLM 转标签 → 出图 → 挂回消息）写在单人聊天 Activity 里，
群聊要用只能复制一遍。现在抽成 `chat/QuickImage`：调用方只传「取哪个 controller」和两个
UI 回调，单人聊天与群聊共用。顺手修掉一个隐患：群聊出图期间切频道，**图只落到发起时的频道**
（`target` 在点下那一刻锁定，不再每次回调重新取当前频道）。

单条消息也能配图（长按 / 点气泡菜单 → 配图），锚点就是那条，上下文不会带错。

### 40.4 验证

- `stcore` 224 个单测（新增 2 个旁白导出 / 往返用例）、`app` 37 个全绿
- `tsc --noEmit`、`npm run build`、`:app:assembleDebug` 通过
- 用 esbuild 单独跑了一次 `assemblePrompt`：带 `narrator` 时 system 插在用户角色之后、
  第一条历史之前；不带时消息数组逐字节不变
