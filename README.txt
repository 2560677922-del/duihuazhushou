冒险模拟器 · AI 写作 + 冒险平台
================================================

一个自用的 SillyTavern 兼容型 AI 写作 / 冒险工具。
PC 浏览器 + Android APK 两端使用，数据全部本地保存。

========================================================================
【战略】浏览器端已基本收工，接下来专注移动端
========================================================================

方向（2026-10 决定）：
  · 浏览器端定位为"能用就行"，不再为它花时间
  · **移动端是主战场**，可以只给手机做的功能
  · 不被"只能用某架构某语言"框住 —— 手机端有多种实现路径，
    只要能更流畅就用（原生壳、混合渲染、按页面分包、Worker 搬运重活…）
  · 硬约束：**世界书 / 预设 / 角色卡 / 正则 必须继续兼容傻酒馆**
    这部分已完成，是不能破坏的资产。其余功能都可以为了移动端重做。

待办的前置问题（详见第五节"已知问题"）：
  存储层改成惰性取图后，**图片显示是否正常还没验证过**。
  这条不确认之前不要动架构 —— 在坏地基上重写是白费力气。

一、怎么跑起来
------------------------------------------------------------------------

开发（局域网内手机也能访问）：
    npm install          （首次）
    npm run dev          （启动，端口 5173）

打包 APK（Android）：
    npm run build                              先出 dist/
    cd dbpg
    gradlew.bat :app:assembleDebug --console=plain
    产物：dbpg\app\build\outputs\apk\debug\app-debug.apk
    （别用 build-apk.cmd，它末尾有 pause 会卡住）

装好后：设置 → 关于 → 🔄 检查更新，强制刷新到最新版本。

三、几个容易搞混的概念（重要）
--------------------------------------------------

① 对话模型的「运营商」和「模型」是两层
   一家运营商 = 一个地址 + 一个密钥。下面可以挂多个模型。
   加模型时地址和密钥自动继承，不用重填。
   （老数据里每条记录都自带一份地址密钥，现在会自动同步成一组。）

② 生图的「接口」和「风格」也是两层
   接口 = 怎么连上去（地址/密钥/模型）
   风格 = 出什么画风（画师串/反向词/采样器/尺寸/seed）
   两者独立组合，比如同一套接口配「清新」和「暗黑」两套风格。

③ 两张「参考图」不是一回事
   风格参考图（风格卡片上那张）= 只用来看画风效果的缩略图，不参与出图。
   对话参考图（对话界面那张）= 真的驱动图生图，通常是角色形象/立绘。

④ 正则的三种作用时机
   通用（没标）      → 显示 + 上下文 + 导出 都生效
   promptOnly        → 只改发给模型的文本
   markdownOnly      → 只改显示（美化 UI 用，永远不会污染上下文）
   所以导入别人的美化正则，不用担心它会改坏对话。

⑤ 图片标记 [[IMG: 描述]]
   写在正文里，发送前会被统一剥掉，模型再也看不到它。
   图片以附件单独存放，不占 token。开启自动配图后由 AI 自行决定插图位置。

四、数据存在哪
--------------------------------------------------

浏览器 / APK 里都是 IndexedDB + localforage。

dev 模式下 vite 插件会把它同步成可读文件：
    data/app-data.json          ← 当前真实数据（备份这个即可）
    data/backups/               ← 每次写入前的自动快照，保留最近 20 份
    data/.clean-baseline.json   ← 测试用的干净基线（别手动改）

data/ 已被 .gitignore 忽略（里面有 API 密钥，绝不能提交）。

换设备：旧设备复制 data/app-data.json → 新设备覆盖同名文件 → 打开 App。

    node node_modules\vite\bin\vite.js --host 127.0.0.1 --port 5173

⚠ 不要在 dev server 跑着的时候往 scripts\ 里写新脚本 ——
   Vite 的文件监听会撞上写了一半的文件并报 EBUSY 直接退出。
   先在别处写好再拷进来，或者先停掉 dev server。

⚠ dev server 请监听 **127.0.0.1**（不要用 localhost）。落盘是按访问来源

   你真实数据的那 4 个来源（192.168.31.45:5173 / localhost:5173 / …）。
   这也是 _verify.mjs 里写死 192.168.31.45 的原因。

⚠ 测试纪律：任何会改数据的测试，一律用
    import { withCleanData } from './_testdata.mjs';
    await withCleanData(async () => { ... });
它从不可变基线恢复并在 finally 里还原。
曾出过事故：脚本用「开头备份/结尾还原」，中途抛错就没还原，
把用户真实的模型名、预设、温度都改掉了。所以别再用老写法。

七、给下一个接手的说明
--------------------------------------------------

几个反直觉的地方，改之前先读完再动：

· 背景必须挂在 html 上，不能挂 body。
  html 一旦自己有背景，body 的背景就不再传播到 canvas，
  长页面滚到底会露出 html 的底色（"变黑"就是这么来的）。

· 手机上 `.row > .col` 那条 flex 规则带 !important，不能删。
  模板里大量内联 style="flex: 2"，内联样式优先级高于样式表，
  不加 !important 的话移动端布局会整个失效（字段被压成竖条）。

· 消息气泡上有 content-visibility: auto（长对话性能优化），
  它会成为 position: fixed 后代的包含块 —— 全屏浮层必须用
  <Teleport to="body"> 送出去，否则会被关进气泡里。

· 主色 token 全在 appearance.apply() 里写内联到 :root，
  因为内联自定义属性优先级高于样式表，别指望 CSS 里写主题色。

· 底部标签栏高度是 --tabbar-h（63px）。
  进二级聊天页时 MainLayout 把它设成 0，
  所有按它定位的抽屉/吸底输入框会自动贴底，不用逐个改。

九、UI 方向（2026-10 决定，待细化）
========================================================================

用户要求：**内在逻辑不动，UI 换成安卓原生那套**（聊天界面也一起）。

⚠ 动手前必须先定清楚"原生壳"指哪一种 —— 在 Android 上是三件差很大的事：

  A. 保留 Vue，只把界面做成原生 Material 风格
     · 业务逻辑、页面模板一行不改
     · 换：配色/圆角/间距/动效/手势/键盘处理/状态栏，做成 Material 3
     · 加：Capacitor 插件（触感反馈、系统分享、原生选择器、返回键）
     · 工作量：小        风险：低     跟手性：明显变好

  B. Kotlin 原生 Activity + WebView 装内容
     · 原生写导航栏/底部栏/输入框，网页只负责正文
     · 每一处交互都要写桥（取值、传值、回传）
     · 工作量：大        风险：中     跟手性：好
     · 注意：Bridge 里每多一个方法，就多一处能出 bug 的地方

  C. 换框架（Flutter / React Native / Compose Multiplatform）
     · UI 用新框架重写，业务逻辑（引擎/存储/傻酒馆兼容）保留
     · 但页���模板几乎全部要重写 —— 现在代码量的大头就是 .vue 模板
     · 工作量：最大      风险：高     跟手性：好

★ 我的建议：A 优先，B 只在 A 做完还不够时才考虑，别直接上 C。
  理由：已经有实测证据 —— 上一轮标签页卡 16 秒，根因是一行冗余代码，
  不是框架不够原生。原生化解决不了那类问题。
  而 A 能拿到"看起来/摸起来像原生"的绝大部分体感，
  成本只有 B/C 的零头，且一行业务逻辑都不用动。

★ 无论选哪个，以下三条铁律不能破：
  1. 傻酒馆兼容（世界书/预设/角色卡/正则）必须在 src/engine 里，不动
  2. 浏览器端要继续能用（拿同一个 dist 跑）
  3. 每一步都要能回退 —— 上一版 APK 永远留着

八、已知问题 / 正在做的事
========================================================================

【卡顿问题 · 已修主体，待做隔离】
用户反馈"越用越卡"，怀疑是图片。

── 已定位并修复（已验证）────────────────────────────
存图时 dataURL 会被"外置"成 blob: 短引用存进独立 IndexedDB，
但**读**的时候 storage.getItem 会调 internalize，
把这次读取涉及的所有图片**全部**还原成 base64 字符串。
  → 打开会话页 = 所有会话的所有图片一次性进内存
  → 50 张图约 70MB 字符串，手机上直接卡死
另有一个 healAttachments 在启动时干同样的事。

已改（storage.ts / lib/lazyImage.ts）：
  · getItem 不再展开引用          → 读数据 0ms，内存只剩短引用
  · 启动自检只查"键在不在"        → 不再把图片读进内存
  · 新增 lib/lazyImage.ts         → 统一按需解析 + LRU（上限 24 张）
  · 图片库、阅读器滚进视口才加载
验证：40 张图会话，读数据 0ms，内存 13MB，裂图 0。
（早前"图片不可用"是测试环境假象：每次测试用了新的浏览器 profile，
  等于全新的空 IndexedDB，上一轮的图自然取不到。同 profile 复测全正常。）

── 待做：三个子应用隔离 ─────────────────────────────
目标（用户明确要求）：
  **看起来是一个软件，实际是三个独立的软件，开机时同时启动、互不影响。**

  ┌─ 主程序 ────────┬─ 图片库 ────────┬─ 生图工具 ──────┐
  │ 聊天/资产       │ 生成图全集中存   │ 标签页直出+参数   │
  │ 自己的 store     │ 自己的 store     │ 自己的 store     │
  │ 自己的存储键     │ 自己的存储键     │ 自己的存储键     │
  │ 懒加载/按需初始化 │ 按需初始化       │ 按需初始化       │
  └─────────────────┴─────────────────┴─────────────────┘
        并行拉起，互不阻塞；任一方的数据量不得拖垮其它两方

具体要拆的：
  1. 图片库从 imageStore.images 里独立出去，自成一套存储
  2. 标签页直出的生图结果不再混进图片库
  3. 三方的 Pinia store 互不引用；一个方的初始化不能 await 到另一个
  4. 界面上：本地库叫"云端"，真 GitHub 叫"备用云端"

★ 图片归属（用户 2026-10 拍板）★★
  **图片本体只存在图片库里，对话里只存一个引用。**
    · 对话记录里存的是 `imageId`（引用），不存图片本体
    · 界面上照样显示、照样能点开 —— 因为第一个库是本地 blob 库，
      取图是同步级的，不会因为"只有引用"而变慢
    · 好处：对话数据（会同步、会落盘、会进 GitHub 备份）里没有图片，
      体积小、不随图量增长；图片库的膨胀完全影响不到聊天页
  → 这条是拆分的**核心动机**，实现时以此为准绳

★ 启动策略（用户拍板）★★
  **开机三个模块全部一起加载，给足时间。**
  不做"进哪个页面才初始化哪个"——手机性能跑得动三个小模块，
  换来的是切换页面零等待。

★ 图片存储换原生（用户拍板）★★
  现在图片走 IndexedDB（浏览器那套）→ **换成安卓原生那套**。
  理由：图片是大块二进制，放 WebView 的 IndexedDB 要走 base64，
        白白多 33% 体积、还要占 WebView 内存；原生文件直接按路径存，
        <img> 用 convertFileSrc 加载，不进 JS 堆。

  ★ 基础设施已就绪（别重复造）：
    · dbpg/app/src/main/java/com/dbpg/duihuazhushou/FileBridge.java
    · src/lib/persistFile.ts 已经在用 @capacitor/filesystem
    → 照着这个现成的通道加"图片文件读写"即可，不用另起炉灶

  ⚠ 必须保留浏览器通道：
    Web 端没有 Filesystem。storage 层要按环境分流
    （Capacitor → 原生文件 / 浏览器 → IndexedDB），
    对上层暴露同一套接口，否则浏览器端会直接崩。

★ "用更现代的架构"怎么落地（我的建议，别走极端）★★
  · 保留 Capacitor + Vue3，**不要整体重写成 Kotlin/Rust** ——
    聊天/资产/傻酒馆兼容这些都跑在上面，重写等于推倒重来，
    风险远大于收益
  · 真正该换的是**存储层和渲染层**（上面两条），
    这两处是卡顿的根，换掉收益最直接、改动最可控
  · 三个模块之间只通过「引用 + 一个窄接口」交流，
    不共享 store、不互相 await —— 这就是"互不影响"的实现方式

做之前先想清楚：
  · 为什么现在会互相影响？（共 store / 共存储键 / 一次性全量加载）
  · 拆完怎么验证真的互不影响？（造大量图测另一个页面的响应）
